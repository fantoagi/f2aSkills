# fanto-article-generator

用于生成 AI 相关内容稿件的专用 Skill，支持五种严格分流的写作模式：

1. **模式 A：系列文章 / 番外篇** — fantoAGI 专栏风格，大白话、强比喻、痛点引入
2. **模式 B：行业快讯** — 接近机器之心/量子位，信息密度高、正式克制
3. **模式 C：AI 一线内容转述** — 公众号长文转述，含对话转述/教程转述/观点转述三个子类型
4. **模式 D：认知重构** — 个人学习视角，“输入-内化-输出”闭环，学习同伴感，协作式写作
5. **模式 R：微调（Light Revision）** — 对已成稿的单点/多点修改，不重跑完整 SOP → `references/mode-revision.md`

## 源材料准备（写文章前必须先完成的硬阻断）

源材料按形态分三类，**进入“模式选择”前必须先确认形态并完成相应抓取/整理**：

### 形态 1：用户直接粘贴文本

- 纯文本粘贴 → 直接作为 `源文本`，无需抓取
- 必须主动询问：**“源文里有没有图？如有请发图或图链接”**——用户说“无图”才能跳过

### 形态 2：本地文件 / PDF / Markdown

- PDF：用 Read 工具读全文（PDF 在 Windows 上 Read 支持）+ 提取图（如有）
- Markdown / 文本文件：Read 全文，**扫描 `![]()` 语法和本地图片路径，把所有图文件复制到 `images_<topic>/`**

### 形态 3：URL（在线网页 / 文章 / 报告）

**禁止**只用 `WebFetch` / `Jina` / `curl` 抓文本——这些纯文本方式拿不到图 URL。**必须用 CDP 浏览器抓全量内容**：

1. CDP `/new?url=` 打开页面
2. 等待 `ready: complete`
3. 扫所有 `<img>` 和大型 `<svg>` 元素，记录 `{src, alt, width, height}` 清单
4. 对每个 `<img>`：
   - 若有真实 `src`（非 lazy-load 占位）→ `curl` 下载到 `images_<topic>/`，命名 `<序号>-<alt 简化>.png`（如有）
   - 若 `src` 为 data-URL 或 lazy-load placeholder → 滚动到该位置触发加载后重试
5. 对每个大型 `<svg>`（width > 200px）：
   - 提取 `outerHTML` 保存为 `.svg`（现代 Markdown 渲染器支持；如目标环境是微信公众号则需后续转 PNG）
   - 备用方案：从全页截图裁切（需 CDP proxy 支持 `fullPage=true`，否则只能滚动 + 截 viewport）
6. 文本：`/eval` 提取 `document.querySelector("main")?.innerText || document.body.innerText`

#### 形态 3 陷阱：React/Next.js 站点的 SVG 元素抓取

Next.js + CSS module 站点（Anthropic、Vercel、Linear 等）的 SVG 时间线/图表经常遇到下面三类问题，**抓取时必须逐项处理**：

**陷阱 A：path 初始 `opacity:0` 靠 JS 动画显示**

React 组件初次渲染时把所有 path/circle/rect 设为 `opacity:0`，靠 CSS transition 或 `@keyframes` 动画到 1。直接 `outerHTML` 提取拿到的 DOM 里所有 path 都是 `opacity:0`。

**处理**：
- 抓图前 `document.querySelectorAll('[opacity="0"]').forEach(e => e.setAttribute('opacity', '1'))`
- 同时处理 `style="opacity: 0;"`（`e.style.opacity = '1'`）
- 注入 CSS 强制覆盖：`svg * { animation-duration: 0s !important; transition-duration: 0s !important; }`
- 设 `--flow-duration: 0s`（很多 React 组件用 CSS 变量控制动画时长）
- 改完后 `wait 2s` 让 React 重渲染稳定再截图

**陷阱 B：`<use href="#icon-xxx">` 引用的 symbol 在 chrome 直接打开 .svg 文件时不渲染**

`outerHTML` 提取的 SVG 脱离原页 CSS module 后，`<use>` 引用 `<symbol>` 时渲染 0×0。`<use>` 自身需要 `width` `height` + 显式 `x` `y` 才会被 chrome 实例化。

**处理**：
- 方案 1（推荐）：**不要单独打开 .svg 文件**。直接在原页用 `Page.captureScreenshot` clip 或 fullPage 截全页，再用 PIL 裁出 SVG 区域。这样保留原页 CSS + React 状态
- 方案 2：手动给所有 `<use>` 补 `x` `y`（用 Python 解析 SVG 算出每行 stage 的坐标）
- 方案 3：把 `<symbol>` 内容直接 inline 展开到 `<use>` 位置（脚本处理复杂）

**陷阱 C：CSS variable `var(--xxx)` 在脱离原页后未定义**

原页 SVG 用 `var(--border-subtle)` / `var(--text-primary)` / `var(--accent-primary)` 等 CSS 变量定义颜色，CSS module 注入时这些变量被赋值。提取 SVG 时这些变量 fallback 为 `unset` → stroke/fill 透明。

**处理**：
- 抓取时直接 `/eval` 读 `getComputedStyle` 获取 CSS variable 实际值
- 或在原页截图（方案 1）—— 不需要单独处理变量

**首选方案**：始终在原页用 `Page.captureScreenshot` 截全页 + PIL 裁剪。**避免**单独提取 SVG 元素保存。**避免**把 SVG 文件本地打开再截图。

#### 形态 3 配套工具：CDP proxy 必须支持的功能

如果 web-access skill 的 `cdp-proxy.mjs` 还没支持以下端点，需要扩展：

1. **`/viewport?target=X&w=1280&h=2000`** — `Emulation.setDeviceMetricsOverride`，让 SVG 在 viewport 内可见
2. **`/screenshot?target=X&fullPage=true`** — `Page.captureScreenshot` 带 `captureBeyondViewport: true`，截全页
3. **`/screenshot?target=X&clipX=&clipY=&clipW=&clipH=`** — `Page.captureScreenshot` 带 `clip` 参数，截指定矩形区域

（2026-06 实测 anthropic.com/institute/recursive-self-improvement 抓取：缺这 3 个端点需要先扩展 proxy，再走“viewport 调大 + fullPage + PIL 裁剪”流程，详见 `cdp-proxy.mjs` 改动历史）

**图片清单与位置对齐**（写文章阶段必填）：

| # | 文件名 | 原始 alt 摘要 | 文中位置锚点 |
|---|--------|--------------|------------|
| 00 | `00-timeline.svg` | 时间线：人在 AI 开发流程中的角色演变 | 开篇“## 从人在回路到AI自主开发”后 |
| 01 | `01-code-per-quarter.png` | 工程师每季度代码合并量 | “下图展示了这两次拐点”后 |
| ... | ... | ... | ... |

**硬底线**：URL 源材料抓取后，阶段一必须先在对话中输出“图片清单与位置对齐表”。无图也要显式声明“扫描结果：0 张图”——避免漏抓。

#### CDP 不可用时的降级补偿协议（强制，不可跳过）

当环境不支持 CDP 浏览器（如无 Chrome/ChromeDriver、CDP proxy 不可达）时，允许降级为 curl 抓取，但**必须执行以下补偿步骤**，否则视为源材料未准备完成：

1. **curl 下载 HTML 全文 + 图片**：`curl -sL <URL>` 保存 HTML，扫描 `<img>` 标签提取 `src`，下载所有非装饰性图片到 `images_<topic>/`
2. **提取链接清单（新增，防链接静默丢失）**：扫描 HTML 中 `<article>`/`<main>` 区域内所有 `<a href="...">锚文本</a>`，记录 `{href, 锚文本, 所在段落}`。**提取正文文本时禁止** `re.sub(r'<[^>]+>', '', body)` 直接剥标签——那会同时剥掉全部 `<a href>`。必须把 `<a href="URL">文本</a>` 原位转换为 `文本 <URL>` 保留在源文本中（参考文献条目同样在条目末尾附 `<URL>`）
3. **从 HTML 中提取图片上下文**：对每张下载的图片，在 HTML 中定位其前后 500 字符的文本上下文，记录：
   - 图片在 DOM 中的位置（哪个 `<section>` / `<h2>` 之后？前一个 `<p>` 的内容是什么？）
   - 图片的 `alt` 属性（如有）
   - 图片紧邻的文本片段
4. **输出“图片 + 链接双清单”（强制）**：图片清单格式同 CDP 版本，`文中位置锚点` 列标注置信度 `[推测]` / `[已确认]`；链接清单列出全部 `{锚文本, URL, 位置}`，翻译时逐条对照
5. **翻译阶段强制引用**：翻译执行时，每完成一个章节：检查该章节是否有对应配图 → 有则立即插入 `![](./images_<topic>/XX.png)`；检查该章节是否有原文链接 → 有则立即在对应锚文本后补 `<URL>`
6. **交付前校对**：发布/交付前，逐张确认每张下载的图片在译文中有至少一处引用；跑 `python scripts/check_links.py <源.html> <译文.md>` 确认链接保真（exit 0）

> **为什么需要补偿协议**：curl 只能拿到 HTML 文本和图片 URL，丢失了图片与文本的 DOM 位置关系；且纯文本提取若直接剥标签，`<a href>` 链接会与标签一起被剥掉。不加补偿步骤，翻译者看到的源材料是“无图无链接的纯文本”，译文中自然不会有图和链接——图片问题发生在 2026-08-02 Anthropic containment 文章（5 张图全部下载成功，0 张出现在译文中）；链接问题发生在 2026-08-04 Lilian Weng harness 文章（45 个正文内嵌链接 + 39 条参考文献链接全部静默丢失，交付闸门未能检出，因为闸门对比的是提取后文本，源侧计数恒为 0 恒等通过）。

**反例**（2026-06 实测）：用 `Jina + WebFetch` 抓 anthropic.com/institute/recursive-self-improvement 全文时只拿到 33KB 文本，**漏掉了 4 张原图**（时间线 SVG、代码产出图、成功率图、研究判断对比图），文章全部用“图表说明”引用块文字占位。后续补救消耗多轮上下文。

## 模式选择（写文章前必须先判断）

**默认：模式 A（系列文章 / 番外篇）。**

触发模式 A 的关键词：番外篇、系列文章、fanto 风格、沿用之前专栏风格

触发模式 B 的关键词：行业快讯、快讯稿、媒体稿、行业媒体风格、像机器之心、像量子位、科技媒体快讯

触发模式 C 的关键词：对话转述、访谈转述、播客整理、演讲整理、公众号转述、转译、对话全文、对话整理、转述文章

触发模式 D 的关键词：学习、实践、学习分享、认知升级、认知重构、学习笔记、试用体验、踩坑记录

### 意图优先级（关键词冲突时使用）

当用户表达同时命中多个模式时，按**写作目标**而不是单个关键词判断：

1. 目标是忠实整理一场访谈、播客、演讲或对话 → **模式 C**
2. 目标是写作者自己的学习变化、实践体会、踩坑经验 → **模式 D**
3. 目标是报道产品发布、模型更新、行业动态 → **模式 B**
4. 目标是解释一个 AI 概念、机制、方法，或一个 AI 相关的职业/领域/角色（如 FDE、提示工程师）→ **模式 A**（进入模式 A 后先按 mode-a.md 步骤 1.5 判定概念类型，再选骨架 A1/A2/A3）

如果仍然无法判断，先简短确认目标；不要把模式 C 的来源保真、模式 D 的个人视角、模式 A 的大白话比喻和模式 B 的快讯调性混在一篇里。

## 总原则

- 五种模式**严格分流**，不要混写调性。
- **去模板化原则**：所有模式的核心骨架可以复用，但过渡句、结尾句、导语收尾等高频暴露的文本必须每篇独一无二。读者看到同一句话两次就会归类为 AI 水文。
- **链接格式化规则**：来源链接使用 `<URL>` 格式（Markdown autolink 语法），不用 `[text](url)` 链接语法。`<URL>` 可确保微信公众号/CMS 渲染器将 URL 自动转为可点击链接，同时避免中文标点被吞进链接。禁止裸 URL 不加 `<>` 包裹。
- 默认输出中文。除非用户明确要求英文或双语，不输出英文正文。
- **英文源材料翻译工作流（轻审计硬阻断，不可跳过）**：英文参考材料 → **必须先读完 `references/ai-translation-guide.md` 和 `references/translation-principles.md` 全文** → 先输出轻审计闸门（风险等级、术语清单、代码块清单、3 个高风险句校验、先翻译再改写确认）→ 低风险材料执行轻审计翻译，高风险材料升级完整审计 → 再按目标模式改写。**禁止在读完翻译指南和原则文件之前开始翻译。禁止跳过翻译步骤直接“提炼事实+重写”。禁止直译成生硬中文。** 翻译前最少必查：`translation-sop.md`（4 阶段工作流编排器）→ `translation-principles.md`（五条原则 A-E）→ `glossary-ai.md`（术语）→ `translation-quickref.md`（模式速查）→ `translation-checklist.md`（交付前打勾）。**软错层**额外查 `editor-polish-checklist.md`（12 节软错清单）+ `cross-cultural-terms.md`（跨文化术语库）。**L0 反幻觉闸门**做 `source-inventory-protocol.md` 的 3-4 张源 dump。
- 文章中引用的图片必须下载到本地后用相对路径引用，不要使用远程 URL（微信公众号发布时 wenyan 无法拉取 CDN 远程图片）。图片统一放在文章同目录下 `output/<topic>/images_<topic>/`，文中引用 `./images_<topic>/xxx.jpg`。
- **Twitter/X 源材料强制规则**：X/Twitter 的图片嵌在 DOM 中，**纯文本方式（WebFetch/Jina/curl）拿不到图片 URL**。X/Twitter 源必须先走 CDP 浏览器获取完整内容（文本 + 图片）。优先使用 `scripts/extract_x_thread.py` 一键提取，脚本自动处理滚动、懒加载等待和位置标注。手动流程：CDP `/new?url=` 打开推文 → **先 `/scroll?direction=bottom` 滚到底触发 thread 续篇懒加载**（图片不滚动不进 DOM，`querySelectorAll` 返回空不代表无图） → 等待图片加载完成 → `/eval` 提取 `document.querySelectorAll('img[src*="pbs.twimg.com/media"]')` → count > 0 则下载，count = 0 则判定无图继续（滚动后仍为空才算真的无图） → 下载图片到 `images_<topic>/` → **每张图必须记录 `tweet_index`（属于 thread 中第几条推文）和该推文的文本内容**，写文章时按推文顺序插入配图，不得凭感觉重排。
- **X Article（长文）vs X Thread（推文串）格式区分**：X/Twitter 上有两种长内容格式，提取策略完全不同：
  - **X Thread**：多条独立推文串联，每条 ≤280 字。用 `extract_x_thread.py` 提取。
  - **X Article**：单篇长文（类似公众号文章），有标题、章节、代码块，可达数千字。URL 格式为 `x.com/<user>/article/<id>` 或推文卡片上显示“Article”标签。**登录墙截断率极高**——`extract_x_thread.py` 通常只能拿到标题和前 1-2 段。遇到 X Article 时的提取优先级：
    1. **镜像站优先**：搜索 `"<article title>"` 找 youmind.com / glean.smartcoder.ai 等镜像全文
    2. **CDP 直接打开**：Chrome 登录状态下直接导航到 X Article URL，等完整渲染后提取 `document.body.innerText`
    3. **WebFetch 降级**：如果镜像和 CDP 都失败，用 WebFetch 抓镜像站
  - **X Article 的代码块和图片**：Article 内嵌的代码块是正文的一部分（不是推文附件），必须完整保留。Article 图片提取分两层：
    - **封面图**：在 DOM 中作为 `<img src="pbs.twimg.com/media/...">` 存在，`extract_x_thread.py` 会自动下载；译文必须把它用作封面——复制为 `output/<topic>/cover.png` 并在 frontmatter 引用 `cover: ./cover.png`（原文封面优先，不重新生成；比例不合 2.35:1 时中心裁切）。
    - **正文内嵌图**：X Article 正文中通常有 3-8 张配图（截图、流程图、对比图），在镜像站中以 `<img>` 标签散布于各章节。**提取时必须同步扫描所有 `<img>` 标签**，按在正文中出现的顺序记录 `{url, alt, section_heading}`，下载到 `images_x_thread/`，命名 `x_media_02.jpg`、`x_media_03.jpg`……写文章时在对应章节插入 `![](images_x_thread/x_media_XX.jpg)`。
    - **嵌入视频**：X Article 可能含 `<iframe>` 嵌入视频（Cloudflare Stream / YouTube）。微信公众号不支持 iframe，在对应位置插入文字说明 + 视频链接，如 `> 📹 演示视频：[点击查看](url)`。
  - **反例 1**（2026-06-29）：Raytar 的 X Article “Stop Being the Loop” 原文含 6 张正文配图 + 1 个嵌入视频，翻译后仅保留封面图，正文 0 张图。根因：从镜像站提取全文时只取了文本，未扫描 `<img>` 标签。
  - **反例 2**（2026-06-29）：同一篇文章被错误地用 OfficeChai/TheNewStack 二手文章替代翻译，代码块全部丢失。根因：未识别 X Article 格式，`extract_x_thread.py` 登录墙截断后未触发镜像站回退。
- **Twitter/X 配图 GIF 检测**：检查 DOM 中是否有 `tweet_video_thumb` 或 `tweet_video` 标签，如有则下载 MP4 并用 OpenCV + PIL 转换为 GIF（~20 帧、宽 900px、PIL quality 70、100ms/帧、≤5MB）。环境无 cv2 时先 `pip install opencv-python`。
- **X/Twitter 改写阶段图片引用路径强制（G8 硬约束）**：改写阶段必须先读 `x_thread_manifest.json` 的 `images`、`videos`、`video_thumbnails` 三个数组的所有 `local_path`，文章正文中所有 `![...](...)` 格式的图片引用，**路径必须严格等于 `local_path` 字段值**（含 `images_x_thread/` 前缀和文件名）。不得自由发挥路径、不得使用 CDN 远程 URL、不得遗漏文件名前缀、不得自创未在 manifest 出现的图片引用。这是模式 C 自检 9.11 的硬约束——交付闸门第 16 项会逐项核对。
- **X 改写阶段图片位置锁定（G6 硬约束）**：改写前必须先读 `x_thread_manifest.json`，把 `images`/`videos`/`video_thumbnails` 的 `tweet_index` 与“推文→章节映射表”对齐，输出“图片位置确认表”（见 mode-c.md Step 3.6）。一张图 `tweet_index` 只能落到“涵盖该 tweet_index 的章节”，**不得跨推文移动配图位置**——这是 X 配图最容易出错的地方。
- **X 视频/GIF/MP4 提取依赖**：跑 `extract_x_thread.py` 前确保 `pip install opencv-python Pillow websocket-client` 已装。环境无 cv2/PIL 时脚本不会崩，会降级为“返回 MP4 原始文件 + build_warnings 报警”，静态图流程不受影响。

## 工具链操作铁律（2026-08-05 首沉，2026-08-12 增审校/发布原子性）

以下 9 条操作错误在 2026-06~08 的多次会话中各踩过 ≥1 次，每次浪费 2-5 轮上下文。**违反任一条 = 操作事故，直接按正确做法重来。**

1. **CDP `/eval` 必须用 `-d`（原始 body），禁止 `--data-urlencode`**：proxy 端不做 URL 解码，`--data-urlencode` 会把 JS 表达式编码成 `%28%27` 形式 → 语法错误 Uncaught。正确：`curl -s -X POST "http://localhost:3456/eval?target=X" -d "document.querySelectorAll('img').length"`。排查信号：`document.title` 能执行但 `querySelectorAll` 报 Uncaught、`typeof document` 返回 “number” 等诡异结果。
2. **含反引号或中文引号的 Python 脚本必须写文件再执行**：禁止 `python -c "..."` 或 heredoc 内嵌——bash 会在双引号内执行反引号内容（`irm https://...` 被当命令执行）、中文引号在 GBK 控制台报 SyntaxError。正确：Write 脚本文件（含 `# -*- coding: utf-8 -*-` 头）→ `PYTHONUTF8=1 python 脚本.py` → 删除脚本。
3. **任何 Write/Edit 含中文引号的内容后，必须跑引号重建脚本**：Write 工具与 Edit 操作都可能把全角引号转成 ASCII 或破坏左右交替（本会话 Write 后 23 对全变 46 个半角）。修复脚本：把全文弯引号塌缩为 ASCII → 从左到右重建 `“”` 交替 → 验证 `left==right` 且 `ascii==0`。每次批量修改后必跑。
4. **manifest 类 JSON 的追加操作必须幂等（按 local_path 去重）**：同一个补充脚本跑两次会把图片条目重复追加（本会话 images 6→11）。写脚本时先按 key 去重再写回。
5. **大页面文本提取用分块 slice，禁止单次 innerText**：`innerText` 计算在大 DOM 页面上会触发 Runtime.evaluate 超时。正确：`JSON.stringify(innerText.slice(i, i+4000))` 分段提取后拼接。
6. **空格清理正则禁用 `\s+`，必用 `[ \t]+`**：`\s` 匹配换行符——中英/中数间空格清理时会把换行、空行一并吞掉。2026-08-10 事故：frontmatter title 行与 cover 行合并成一行、2 处章节标题与正文间的空行消失（125 行→120 行）。排查信号：文件行数减少、frontmatter 键值粘连（`意外cover:`）、标题与正文首句粘连（`常态Elad`）。正确：`(?<=[一-鿿])[ \t]+(?=[A-Za-z0-9])|(?<=[A-Za-z0-9])[ \t]+(?=[一-鿿])`；修改后必须验证行数与引号平衡。另注：GNU grep 不支持 `一-鿿` 转义（会静默误报/漏报），Unicode 字符类验证一律用 Python 正则。
7. **发布前冻结内容，标题/封面/正文变更必须先于发布完成（发布原子性）**：发布管线（wechat-draft-publisher 的 preflight → publish）内不做任何内容变更。改标题/封面/正文后必须按序完成：同步封面（`sync_cover.py`）→ 封面 HTML 若内嵌标题则重新渲染封面 → preflight → publish。违反案例：2026-08-12 认知公地一文，publish 调用被用户拒绝后才发现应先改标题、重生成封面——发布与内容变更顺序颠倒，白跑一轮并中断流程。前置判定：若用户指令含“标题改成 X + 重新生成封面 + 发布”，封面重渲染必须在发布之前。
8. **审校意见必须以磁盘文件为准绳，禁止基于对话记忆中的中间版本（审校基线协议）**：多轮审校反复出现版本漂移（2026-08-12 第 6 轮，审校方 3 点意见中 1 点“绝对劣势”对应的文本从未存在于磁盘——融合轮已拒绝该词）根因是审校基于对话旧版本而非落盘文件。执行协议：① 审校前必须 Read 磁盘上的目标文件，意见必须附 `文件:行号`；② 每次裁决后把“已拒绝：X（理由：Y）”记入已决事项清单，新意见先查清单——对已拒事项的再次提出，直接引用原裁决行号，不重复全量论证（认知公地会话中“公共池塘资源必补资源”连提 3 轮）；③ 意见与磁盘不符时，先 grep 验证现状再决定采纳/驳回，禁止无据采纳“幽灵意见”；④ 同一任务审校超 3 轮未收敛时，主动切换到对照版本融合法（找对手改写稿逐句对比），而非继续单点审校。
9. **对外输出纯净版必须与磁盘逐字一致（交付展示规范）**：向用户贴出全文（纯净版）时，① 用 4 个反引号 ```` 包裹整文，防微信/CMS 渲染截断；② 引号必须全角（中文引号），禁止手打半角——输出前用 Python 读文件验证 ASCII 双引号计数为 0 且全角左右平衡。违反案例：2026-08-25 AI 工程技能图谱一文，输出纯净版时误用半角引号，与磁盘 `index.md` 的全角不一致（须先验证再贴）。

### 流程

**1. 判断封面来源：原文有封面 → 跳过本节（封面已在源材料抓取时下载）；原文无封面 → 调用 guizang-social-card-skill：**

**3. 自动同步封面到文章目录：**

```bash
python scripts/sync_cover.py output/<topic>/index.md --guizang-output output/
```

`sync_cover.py` 会：
- 在 guizang 的 `output/` 中找 `wechat-21x9-cover.png`（必）和 `wechat-1x1-cover.png`（选）
- 复制到文章目录 `output/<topic>/cover.png` 和 `output/<topic>/cover_square.png`

- `--21x9 <path>` / `--1x1 <path>`：显式指定源文件（覆盖 `--guizang-output`）

- `--no-frontmatter`：跳过 frontmatter 更新

**4. frontmatter 引用（自动）：**

```markdown
---
title: 文章标题
cover: ./cover.png
---
```

#### [强制输出—阶段四C1.6：回译闭环验证] 有英文原文时强制，无英文原文跳过

**原理**：人格化审校（C1.5）虽然比规则拆分更有效，但审校者和翻译者仍是同一个模型——共享底层盲区。回译闭环利用模型的一个不对称能力：**对比两个英文文本的差异，比判断一个中文文本“是否自然”要可靠得多。** 因为对比是相对判断，自检是绝对判断。

**执行**：

1. **分层抽样**：从 C1.5 润色后的中文译文中，按原文各主章节（`##` 级别）每章抽取 1 段。优先抽取含核心论断、数据、技术因果链的段落。总量 ≥5 段。
2. **回译**：将选中的 5 段中文回译为英文（用与翻译相同的模型即可——这里要测的是“意思变没变”，不是风格）。
3. **逐段对比**：回译英文 vs 原文英文，检查 4 个维度：

| 维度 | 检查方法 |
|------|---------|
| 事实断言 | 回译版中的事实断言和原文一致吗？有没有多出或少了什么？ |
| 数字/时间 | 数字精确一致吗？时间窗口被压缩了吗？ |
| 因果方向 | “A 导致 B”的因果关系方向一致吗？没有反转？ |
| 技术细节 | 架构、数据流、模型行为的描述在回译后仍然等价吗？ |

4. **输出回译验证表**：

| # | 原文段落位置 | 所属章节 | 回译一致性 | 差异说明 |
|---|------------|---------|:---:|------|
| 1 | §X（约第Y段） | 第N章 | ✅/⚠️/🔴 | [无差异 / 列出具体差异] |

- ✅ 回译与原文信息等价
- ⚠️ 轻微差异，不影响核心认知
- 🔴 事实性差异 → **定位对应中文段落 → 修复 → 重新回译该段直到 🔴 清零**

5. **loop-until-dry**：如果第 1 轮回译有 🔴，修复后重新抽样跑第 2 轮。通常 1-2 轮清零。如果第 3 轮仍有 🔴，暂停并报告“回译验证未通过”——这意味着 C1.5 的审校可能引入了新的语义漂移，需要主 agent 人工介入。

##### 强制输出格式

```
=== C1.6 回译闭环验证 ===
抽样段落：5 段（覆盖 N 个主章节）
第 1 轮：✅ X / ⚠️ Y / 🔴 Z
  [如有 🔴，列出并标注修复状态]
第 2 轮（如需要）：✅ X / ⚠️ Y / 🔴 Z
最终：全部 ✅/⚠️，0 🔴 → 通过
=== 回译验证结束 ===
```

> **快路径压缩**：抽样 2 段（首尾各 1 段），单轮验证。有 🔴 不 loop——直接修复后进入 C2。

#### [强制输出—阶段四C2：改写版中文质控] 所有模式强制，改写完成后立即执行

改写阶段产出的新中文句子绕过了阶段二的三道防线。此步骤做两件事：机械扫描 + 口述过滤器。

**扫描范围**：改写版全文（不只是“新增句子”——改写可能在原句里引入新的搭配越界）。全量过，不做抽查。

##### 步骤〇：术语首字母大写预检（C2 扫描前强制，不可跳过）

**背景**：glossary §11 已规定专有名词首字母大写（`Prompt` 非 `prompt`、`Git` 非 `git`），但翻译/改写阶段此规则执行率最低——大脑在读“prompt”时自动将其归类为“已熟知的英文词”而非“需要格式校验的专有名词”。四轮审校实测中，术语小写是仅次于引号排版的第二高频缺陷。

**执行**：C2 扫描前，全文搜索以下模式并逐项修正：

| 模式（正则） | 修正为 | 说明 |
|:---|:---|:---|
| `prompt`（句中小写，非代码块内） | `Prompt` | AI 上下文中的提示词，专有名词 |
| `lint`（句中裸用小写） | `Lint` | 工具名，首字母大写 |
| `cron job`（句中小写） | `Cron Job` | UNIX 守护进程名，专有名词 |
| `token`（AI 计费语境小写） | `Token` | AI 计费/长度单位，专有名词 |
| `alignment`（句中小写，非代码块内） | `Alignment` | 首次出现应 `Alignment（对齐）`，后文统一首字母大写 |
| `capex`（小写） | `CapEx` | 资本支出缩写，必须全大写。禁止 `capex` / `Capex` 等变体 |
| `quadratic` / 中文“二次”裸用 | `二次复杂度（Quadratic）` | 中文字面“二次”存在“第二次”歧义风险，首次出现必须补“复杂度”或 bilingual 标注 |
| `review`（代码审查语境裸用） | `Code Review` | 开发者标准黑话，不裸用 `review` |
| `buzzword`（裸用英文） | `营销热词（Buzzword）` | 泛读者需中文+英文双语标注 |
| 中文技术俚语首次出现（如“刷榜”“越狱”“跑分”） | `针对测试集特化优化（俗称"刷榜"）` | 中文技术圈通用俚语虽可读但精度不够，首次出现必须 paired 到精确技术术语 + 建立概念链（如“刷榜”→“过拟合”） |

##### 步骤〇.5：全局术语替换安全协议（任一批量替换后必跑，不可跳过）

**背景**（2026-08-04 Lilian Weng harness 文章实测）：术语统一/大小写批量替换（如 `harness`→`Harness`、`agent`→`Agent`、`rollout`→`Rollout`）时，裸正则全局替换会误伤三类目标：

- **URL**——大小写敏感，`https://.../2026-07-04-Harness/` 直接 404
- **图片路径**——`01-openai-Agent-loop.png` 与磁盘文件名不符 → 断图
- **英文引文标注**——`Sub-Agent and Backend Jobs`（原文 `Sub-agent`）、`agent runtime`、`patch/diff` 被半改

**执行规则**：

1. **替换前保护**：按行处理时分割并跳过 4 类区域——URL（`<https?://[^>]+>`）、图片路径（`![](...)` 整体）、inline code（`` `...` ``）、参考文献区（`## 参考文献` 之后全部）
2. **单词边界**：`\bagent\b` 而非子串替换；区分大小写（只匹配目标形式，已大写的不会被重复处理）
3. **替换顺序**：长模式在前、短模式在后（“held-in 和 held-out 数据”必须先于“held-out 数据”），否则短模式先替换会破坏长模式的匹配
4. **中英邻接补空格**：替换引入的“英文词紧贴中文”必须补盘古之白（“子 Agent与” → “子 Agent 与”）
5. **替换后强制复验**（任一批量替换后必跑）：
   - `python scripts/check_links.py <源.html> <译文.md>` — URL 保真
   - 图片引用 vs 磁盘文件名逐一比对
   - 引号平衡 + ASCII 直引号 = 0
   - 残留小写清单逐条甄别（引文区/图片路径/参考文献区内的小写属正确保留，正文区残留必须为 0）

**反例**（2026-08-04 实测）：`harness`→`Harness` 全局替换后产生 4 处损坏——URL 404 风险 2 处、断图 2 处、引文破坏 3 处、缺空格 4 处，全部靠人工发现逐一手工修复。本协议把该检查从“事后人工排查”变为“替换后强制复验”。

**⚠️ C2 扫描 4（名词堆叠）误报处理规则**：扫描 4 的正则模式对“的”字连击敏感，会误报以下两类正常中文结构：

| 误报类型 | 示例 | 处理 |
|:---|:---|:---|
| **架构性长名词短语** | `"执行任务的模型和判断目标是否达成的模型，是两个不同的模型"` | **不简化**。此类句子表达核心系统设计原则，技术术语的完整性和对比结构的对称性优先于句长。简化时保留技术动词（`执行任务`、`评估`），只删冗余修饰，不换为口语词（`干活`、`验收`） |
| **口语化自然停顿** | `"你不能让写代码的人给自己的代码打分"` | 保留。中文口语的自然节奏（`X的人给Y的Z打分`）非名词堆叠 |

**判断标准**：遮住扫描器输出，问一句——“简化后，这句话的技术精度或 punch 感下降了吗？” 下降 → 保留原句，标注“扫描 4 误报，保留”。只有既不通俗又不承载技术精度的真正冗余才简化。

#### [强制输出—阶段四C3：口语朗读抽查] 所有模式强制

#### [强制输出—阶段四C3.5：读者视角三问] 所有模式强制（C3 之后、交付闸门之前）

C2 抓硬错，C3 抓语感，但**读者是否真的觉得“这篇文章跟我有关系”——前面全部步骤都回答不了这个问题**。在交付前，用目标读者的视角快速过三个问题：

| # | 问题 | 判断方法 |
|---|------|---------|
| 1 | **3 秒扫读**：读者在公众号列表里划到这篇，只看标题 + 第一段 + 最后一个 `>` 金句——他能立刻知道“这篇文章对我有什么用”吗？ | 如果标题是概括型而非冲突型、第一段是背景交代而非钩子、最后一句是总结而非可带走的具体判断 → ❌ |
| 2 | **噪音测试**：删掉任意一段，文章的核心信息会丢失吗？ | 删除后核心信息仍在 → 那段是填充物 → 砍掉或合并 |
| 3 | **转发动机**：读者转发到群聊或朋友圈时，会配什么转发语？ | 如果你能想出至少一句具体转发语（不是“写得不错”）→ ✅。想不出 → 文章缺少“值得转发的新认知或新数据” |

三个问题任一不通过 → 不追加新内容，而是**删/合并/重写首尾**。此步不增加文章长度，只增加“读者觉得有用”的概率。快路径跳过此步（快路径已有自己的底线）。

#### [强制输出—阶段四C3.6：风格锐化] 模式 C 强制，其他模式可选

C2/C3/C3.5 解决的是“不写错”——没有翻译腔、没有搭配越界、读者觉得有用。但离“极客公园/36氪可发表”还差一层：**“写出好”**——动词的控制感、句子的压缩力、判断的锐度。

此步不做纠错，做**正向注入**。对照目标媒体的语感配置（`references/media-voice-profiles.md`），对全文执行 4 道正向强化：

**锚点约束（R3）：C4 立场句（由阶段四A0定位）为受保护锚点。** 四道强化对立场句——第 2 道压缩、第 3 道"删占位符"一律跳过；第 1 道只允许不改变立场原点的动词微调（不升级成情绪化/营销号腔）；第 4 道只允许不模糊"立场↔转述事实"边界的分句或临界收束。**禁止**改第一人称承诺、削掉限定语、把立场句焊进相邻客观转述句、或增补原文没有的事实。一句话：对立场句**只许加力，不许改立场、不许删、不许压到流失限定**。

##### 第 1 道：动词升级（Verb Power Ladder）

逐段扫读，对每个承载核心动作的动词问一句：**“这个动词在当前语境下够不够力？”**

对照媒体语感配置中的动词力度梯度表（如 GeekPark 的 L1→L2→L3 梯度），将模糊/乏力的动词升级：

| 检查点 | 弱 → 强 | 触发表 |
|--------|---------|--------|
| 核心论断句的动词 | 改变/转变 → **重塑/重构**（范式级）或 **踩下油门**（加速语境） | 句中有 “意味着” / “核心在于” / “本质上” |
| 竞争/对抗语义的动词 | 超越/领先 → **甩开/拉开**（有具体差距数据时）或 **绝尘**（代差） | 句中有具体 benchmark 分差或市场份额数据 |
| 技术动作的动词 | 使用/采用/结合 → **接入/打通/喂入**（按介质选，见 `translation-sop.md` §3.4） | 句中有 API/工具/框架名 |
| 破坏/革新的动词 | 改变/打破 → **刺破/斩断**（结构性的）或 **推倒重来**（成本级的） | 句中有“不再是/取而代之/重新定义” |

**规则**：
- 每 500 字至少升级 1 处动词
- 全文 L3 级动词不超过 3 处（GeekPark/36Kr）/ 不超过 2 处（Juejin，开发者不喜欢过度修辞）
- 升级后必须重读确认：动词力度没有超过原文的事实支撑——因“分差 15 分”而用“甩开”成立了；因“分差 2 分”而用“甩开”是过度修辞

##### 第 2 道：句子压缩（Compression Pass）

逐句问：**“删掉 20% 的字，意思变了吗？”**

目标不是把每句都压成短句，而是**清除无信息量的字**：

| 压缩类型 | 示例 |
|----------|------|
| 删冗余修饰 | “这是一个非常重要的问题” → “这是关键问题” |
| 删“的”字连击 | “在多个硬件平台上都能运行的、由社区维护的编译器” → “开源编译器，社区维护，多平台可用” |
| 删万能动词 | “进行了研究 / 作出了贡献 / 加以利用” → “研究了 / 贡献了 / 利用了” |
| 删“在……的过程中/层面上” | 直接删掉整个框架 |
| 合并同主语短句 | “他打开了电脑。他开始写代码。” → “他打开电脑，开始写代码。”（仅合并非独立信息句；独立论断句不合并） |
| 删“可以说/应该说/不得不说” | 直接说——“不得不说，这个决定是明智的” → “这个决定是明智的” |

##### 第 3 道：判断锐化（Judgment Sharpening）

逐段检查每个判断句，问一句：**“这个判断足够具体吗？换一个编辑，能凭这个判断做出决策吗？”**

| ❌ 模糊判断 | ✅ 锐化后 | 锐化方法 |
|------------|---------|---------|
| 这一变化意义重大 | 这一变化意味着 X 不再需要 Y | 补出“谁在什么条件下不再需要什么” |
| 进一步拉近了与 X 的差距 | 分差从 15 分缩到 3 分，但 X 在 Y 维度仍然领先一代 | 补出具体数据 + 限定条件 |
| 值得持续关注 | 判断信号：看 X 下季度的 Y 数据——如果过了 Z 阈值，就说明…… | 给出可验证的判断锚点 |
| 这是一个重要的趋势 | 如果 X 趋势延续到 Y 时间点，Z 类公司会面临 A 问题 | 补出时间窗口 + 影响对象 |

**规则**：每章至少找出 1 句可锐化的判断。无法锐化的——删掉，那不是判断，是占位符。

##### 第 4 道：节奏变奏（Rhythm Variation）

全文朗读（或模拟朗读），标注句长分布。目标：**不让读者产生节奏疲劳**。

检查：
- 连续 3 句以上长度相近（如连续 5 个 20 字句）→ 插入一个短句（≤10 字）或一个长句（≥40 字）制造变奏
- 连续 3 个 `>` 引用块之间没有过渡句 → 在中间插入一句 10-15 字的过渡
- 连续 2 个 `**加粗**` 判断句之间没有缓冲 → 插入一个不带加粗的陈述句

##### 强制输出格式

```
=== C3.6 风格锐化（目标媒体：[名称]）===
第 1 道 动词升级：[N] 处（其中 L3 [N] 处）
第 2 道 句子压缩：[N] 处，共删减约 [N] 字
第 3 道 判断锐化：[N] 处（其中 [N] 处删除了无法锐化的占位判断）
第 4 道 节奏变奏：[N] 处（短句插入 [N] / 引用间过渡 [N] / 加粗缓冲 [N]）
=== 锐化结束 ===
```

> **快路径压缩**：4 道并为单遍扫读，每道只报告触发计数和 1 个代表性修改。
