# 模式 C：AI 一线对话转述 — 完整规范

> 由 `SKILL.md` 按需加载。
>
> **英文源材料强制流程**：英文播客/访谈/转录 → 必须先读完 `references/ai-translation-guide.md` 按 3 阶段流程做精准翻译 → 再按本模式改写为转述文章 → 完成后对照翻译指南自检清单逐条检查。禁止跳过翻译步骤直接"提炼事实+重写"。

## 🎯 核心写作调性（必须严格遵守）

对话转述模式的目标是把一场重要的 AI 一线对话，用"科技记者整理稿"的质感呈现给中文读者：

1. **记者转述感**：像科技记者在整理一场重要对话——有信息量，有温度，但不是专栏杂谈。你的角色是"转述者"，不是"评论员"也不是"翻译机器"。
2. **大量直接引语**：保留 speaker 的原话质感，让读者"听到"他们在说什么。`"80 倍太疯狂了，是真的扛不住"` 比 `"Dario 表示增速难以承受"` 有力十倍。直接引语优先用粗体强调关键句。
3. **场景化叙事**：每章从对话中的自然转折切入，而不是 `"关于 X 问题，Y 认为……"`。好的引入是 `"Ami 追问：这些趋势会不会反过来改变 Anthropic 训练模型的方式？"`，差的引入是 `"接下来讨论模型训练问题。"`
4. **中文口语化但正式**：不要翻译腔，也不要把烧烤摊大白话带进来。目标语感是"一个表达很好的科技记者在跟你讲他刚听到的一场对话"——自然、清楚、有信息量，但不随意。**等价表达选口语端**：同一语义存在"书面词"和"口语词"两种表达时（如"侧"vs"边"、"亦"vs"也"），选口语端。判断方式：想象你正在跟朋友复述这场对话，你会用哪个词——用那个。
5. **章节独立可跳读**：每章读完后读者都有收获，标题本身就有信息量，支持公众号场景的快速浏览和选择性阅读。
6. **张力驱动叙事**：全文应围绕一个核心矛盾或主线展开——80 倍增长 vs 主动限速、印刷机解放 vs 护城河崩塌。每篇文章在动笔前先想清楚"这一篇的核心张力是什么"。

## 📐 文章固定骨架

### 标题公式

```
核心人物身份 + 冒号 + 最抓眼球的 2-3 个关键词/金句
```

- Boris 篇：`Claude Code 之父 Boris Cherny：编程正在经历自己的"印刷机时刻"`
- Dario 篇：`Anthropic 兄妹档最新对话全文：80倍增长、Amdahl 瓶颈、Mythos 未发布先防御`

规律：冒号前锚定人物，冒号后用具体数据/概念/金句钩住读者。避免空洞的形容词。

⚠️ 公式之上再加"态度钩子"：不只告诉读者"这个人说了什么"，而要传递"为什么你现在需要知道"。有态度：`Dario Amodei：80 倍增长太快了，我们主动踩了刹车`。无态度：`Dario Amodei 谈 Anthropic 的增长与挑战`。

> 标题生成同步参考 `references/shared/title-workflow.md`：模式 C 主推公式 1（人物IP+认知刷新）和公式 3（人物+学习笔记），在现有"人物+冒号+关键词"框架上叠加情绪钩子词。生成标题时按 5 步法打磨。

### 导语三段式

```
[引用式概括] → [时间地点人物上下文] → [话题弧线 + 过渡句]
```

- **引用式概括**：一句 `>` 引用块，高度概括这场对话的核心主题。例如 `> 半小时对话，Dario 和 Daniela 密集输出了 Anthropic 在指数曲线上的体感、取舍和下一步判断。`
- **上下文段**：1-2 句交代时间、场合、人物及其身份。例如 `5 月 6 日，Anthropic 在旧金山办了第二届 Code with Claude 开发者大会。新任 CPO Ami Vora 跟 CEO Dario Amodei、总裁 Daniela Amodei 坐下来聊了半小时。`
- **话题弧线 + 过渡句**：一句话勾勒对话从哪到哪，然后用一句**独一无二的过渡**引入正文。过渡句必须每篇不同——可以是一个问题、一个悬念、一句直接引语的预告。禁止使用模板化表达如"这场对话的信息密度极高。以下是完整整理。"好的过渡：`这半小时里 Dario 说了三次"我们错了"。` / `Ami 的第一个问题就让全场安静了。` 差的过渡：`以下是完整整理。` / `本文为你梳理了关键观点。`

### 正文分章：8-10 节

每章从场景/问题切入，核心观点用直接引语呈现。**不要求每章机械套用同一公式**，允许节奏变化：

- **对话实录型章节**：几乎全是直接引语推进，少量过渡句
- **记者概括型章节**：用自己的语言归纳一段对话，偶尔插入关键引语
- **冲击型段落**：单行引语独立成段，制造阅读停顿

```
## 数字序号、观点金句标题

[场景切入] → [核心观点：引语 + 解释] → [细节展开]
```

标题用 `## 一、二、三……` 编号，后跟该章最核心的观点或金句。

### 结尾两段式

```
[总结升华段] → [来源标注行]
```

- **总结升华段**：回到全文的核心张力，用一两句话提炼深层含义。不重复前文，而是给读者一个"带走的认知"。
- **来源标注行**：斜体，两行格式。第一行交代出处信息，第二行 `<URL>` 格式（Markdown autolink 语法，不用 `[text](url)`）。`<URL>` 可确保微信公众号/CMS 渲染器将 URL 自动转为可点击链接，同时避免标点被吞进链接。硬性格式为：
  ```
  *本文内容全部来源于 [来源名] [场合/日期] "[环节名/标题]"。*
  *来源：<https://...>*
  ```
  如有多个来源如实列出。

## 📐 教程转述骨架（C-tutorial 专用）

> **适用源材料**：X Article 教程、how-to 指南、步骤式教程（如 "10-Step Second Brain"、"Stop Being the Loop"）。
> **与对话转述骨架的核心区别**：教程转述不要求"大量直接引语"和"张力驱动叙事"，保留原文的步骤结构，但用科技记者的简洁语感重写每一步。

### 标题公式

```
核心价值承诺（动词开头）+ 破折号 + 行动钩子
```

- ✅ "让 Claude 读懂你的 Obsidian 笔记——10 步搭建第二大脑，从此不再重复解释自己"
- ✅ "Claude Code 之父不再亲手写 Prompt 了——你的第一步循环，复制粘贴就能跑"
- ❌ "10 步教你搭建第二大脑：完整教程"（无行动钩子）

### 开篇：场景 + 痛点（1-2 段）

```
[一句话场景锚定] → [痛点共鸣] → [解决方案预告]
```

- **场景锚定**：用一个具体人物/场景开头，让读者代入。如 "里斯本有一位 30 岁自由开发者…"
- **痛点共鸣**：描述读者正在经历的困境。如 "每个项目都是同样的开头——花 20 分钟凭记忆重建上下文"
- **解决方案预告**：一句话概括这套方案能做到什么。如 "一个晚上的部署。一个每天早上 7 点自动归档的知识库"

### 正文：步骤式

每步一个 `##` 标题，保留原文的编号结构。每步内部结构：

```
## N. 步骤标题（中文，可加英文术语）

[做什么] → [怎么做（含代码块/命令）] → [验证方式（可选）]
```

- **步骤标题**：简短有信息量，不用 "Step 1" 这种无意义标题
- **代码块**：必须完整保留，加语言标签（如 ` ```text `）
- **图片**：原文有内嵌图时，在对应步骤插入 `![]()`，不得省略
- **每步独立可读**：跳读任一步骤都能理解

### 结尾：效果对比 + 来源标注

```
[Before/After 对比段] → [来源标注行]
```

- **Before/After 对比**：用 "之前…之后…" 结构收束全文，让读者看到转变的完整弧线
- **来源标注行**：同对话转述骨架格式

## 🧩 章节类型菜单

从已验证文章中提炼的 7 种章节角色，按需选用和排序：

| 角色 | 功能 | 选用规则 |
|------|------|---------|
| **人物色彩章** | 建立人物形象，让读者"认识"这个人——有趣的习惯、比喻、反差 | 推荐放在第 1-2 节 |
| **核心数据章** | 最炸裂的数字或事实，制造冲击和记忆点 | 必选，尽早出现 |
| **概念定义章** | 解释一个贯穿全文的关键理念或框架 | 有则必选 |
| **宏大叙事章** | 历史类比或理论框架包装，提升文章高度 | 有则选，与概念章可合一 |
| **深度展开章** ×2-3 | 逐层展开核心论点，每个论点独立成章 | 必选，是文章主体 |
| **展望预测章** | 收束到对未来的判断或期待 | 推荐放倒数第 1-2 节 |
| **收尾缓冲章** | 轻松/人文内容，让读者带着温度离开 | 有则选，放在最后一节 |

组合原则：
- 每篇至少包含：人物色彩章、核心数据章、深度展开章 ×2-3
- 人物色彩章和核心数据章可以前置互换，取决于哪个更有冲击力
- 宏大叙事章可以跟概念定义章合为同一节（如 Amdahl 定律同时承担两个角色）
- 收尾缓冲章不可强求——源材料有温暖的细节才用，不要编造
- **单人长文变体**：当源材料是单作者长文（非多人对话）时，对话转述的两个天然优势——人物色彩和对话节奏——都不可用。需要以下替代策略，否则文章会退化成"逐段翻译"：
  1. **跳跃开头替代人物色彩章**：从原文最反常识/最意外的观点切入，替代"对话中第一个有趣的细节"。示例：`RISC-V 创始人 David Patterson 发了一篇长文。不是讲指令集，是讲 AI 芯片的能耗墙。他开篇第一句话就否定了自己过去 20 年的工作。`
  2. **论点弧线替代对话弧线**：单人长文没有"话题从 X 开始，穿过 Y，停在 Z"的时间线——但它有一条论点弧线（假设 → 论证 → 反驳 → 结论）。导语中勾勒论点弧线替代时间弧线。
  3. **引用块替代直接引语**：单人长文无法"大量直接引语"，但可以从原文中提取 3-5 个关键段落作为 `>` 引用块，制造阅读节奏。这些引用块承担对话模式中"直接引语"的停顿和冲击功能。
  4. **作者立场章节替代人物色彩章**：如果作者有明确的学术/行业立场（如"David Patterson 是 RISC-V 的创始人，这本身就是他的立场声明"），可用 1 段说明，帮助读者理解作者视角的来源和局限。
  5. **反对/争议视角强制补充**：单人长文缺乏对话中的追问和反驳。如果原文未提及反对意见，**每篇必须在倒数第二节用 1 段标注"本文未涉及的反面观点"**——不说"缺点"，只标注原文作者没有讨论的方向。格式：`> 🧭 本文未展开的方向：[1 句话说明]`。这是弥补单人长文"无对话"结构缺陷的最低成本方式。

## ⚠️ 硬性质控规则（最高优先级）

这三条规则高于所有写作技法，写完后必须逐条对照检查。

### 规则一：来源保真——所有内容均源自原始素材，不得扩充、联想

这是底线规则。文章只做"转述、整理、翻译"，不做"扩展、补充、联想"。

- ✅ 可以：从源材料中提取观点，用中文重新表达，保留原话引用
- ✅ 可以：对源材料中分散的相关内容进行归类整理
- ✅ 可以：为中文读者不熟悉的专有名词、项目名称、行业事件补一句不超过 30 字的背景说明（如"Alpaca 是 Dubois 在斯坦福期间发起的开源指令微调项目"），格式为在名称后紧跟括号注释。此条不视为"扩充"——英文听众共享的背景知识，中文读者需要这些桥接才能理解对话含义。超过 30 字或涉及争议性背景判断的，改用编辑注格式 `> 💡` 放在段尾
- ❌ 禁止：添加源材料中未提及的背景知识、历史掌故、行业新闻
- ❌ 禁止：把 speaker 的观点引申到其他领域或与别的事件做连接
- ❌ 禁止：加入自己的分析、评价、或"这意味着……"式的推论
- ❌ 禁止：为丰富内容而从其他渠道补充信息

**检查方法**：文章中的每一句话，都能在源材料中找到对应。找不到的，删掉。

**允许的编辑提炼**：每章末尾可以用一句 "编辑注" 提炼本章关键信号，格式为 `> 💡 [一句话提炼]`，与源材料内容明确区分。这是帮读者抓住主线——转述者对读者负责任的体现。但编辑注不可加入源材料没有的事实或判断。

**编辑注正向质量标准**（不是"不写烂"，是"写出好"）：

好的编辑注满足以下三条——缺一条就删掉该编辑注，不要为了有而加：

1. **定位论证位置**：点出该概念/观点在全文论证链中的位置，而非概括原文。`"这是整篇文章的技术核心"` ✅（定位）。`"纳德拉认为企业需要学习循环"` ❌（概括——原文已经说了，没有信息增量）
2. **信息增量 ≥ 1**：必须包含一个原文隐含但未展开的洞察。`"企业的资产不再仅仅是代码或数据，而是其'消耗 Token 产生业务价值'的系统能力"` ✅（原文没有这句话，但它是从 Token Capital 概念推导出的读者友好解读）。`"Token 资本是企业构建的 AI 能力"` ❌（原文已明确说了）
3. **非必要不加**：如果本章的正文本身已经足够清楚——读者读完不需要额外桥接就能抓住关键信号——就不加编辑注。上限：全文 8 章 → 最多 5 处编辑注。编辑注越多，每处的权威感越低。

不符合上述任一 → 删除该编辑注。

### 规则二：中文表达检查——对照翻译指南逐条检查

翻译完成后对照 `references/translation-checklist.md` 逐项检查：

- **翻译腔排查**：英文被动语态直译（"被允许"→"可以"）、长定语堆叠、代词指代不明、`when` 引导的状语从句直译
- **转录清理**：口语填充词（um, you know, like）、重复、口误、不完整句——转录可忠实保留，但文章应整理通顺
- **中文常见坑**：
  - "在这个层面上" → 删，"层面"是 level 的幽灵
  - "作为一个 X 来说" → "作为一个 X"或直接省略
  - "这是非常有趣的" → 除非真的有趣，否则删
  - "降了 X 倍" → 中文"倍"只用于增，降用"降到原来的 X 分之一"
  - "关于……的问题" → 删"的问题"
  - "在……的过程中" → 删或改写
- **数字/专名/术语准确**：源材料中的数字、人名、产品名、公司名必须与原文一致，不凭记忆写

### 规则三：原文配图必须保留，位置必须对齐原文上下文

**硬约束：原文有内嵌图时，译文必须在对应章节插入 `![]()`。正文图片数量差异超过 50% 即视为翻译未完成。**

#### X Thread 源材料

- 原始博客/翻译中的配图、截图可以直接复用
- **配图位置必须与原文一致**：每张图属于源材料 thread 中第几条推文，转述文章中就放在该推文对应的内容段落后，不要凭感觉重新排布。同一推文有多张图时，按 `img_index_in_tweet` 顺序排列
- **获取配图时同步提取位置信息**：从网页源抓取图片时，不要只提取 URL，必须同时记录每张图的 `tweet_index`（属于第几条推文）、该推文的文本摘要、该推文中总共有几张图。用于写文章时精确还原图文对应关系，不得跨推文移动配图位置

#### X Article 源材料

- **封面图**：下载并引用到 frontmatter `cover` 字段；原文封面优先——复制为 `output/<topic>/cover.png` 直接用作译文封面（比例不合 2.35:1 时中心裁切），只有原文无封面时才生成新封面
- **正文内嵌图**：按在原文中出现的顺序，逐一下载到 `images_x_thread/`，在译文对应章节（同一 `##` 标题下）插入 `![](images_x_thread/x_media_XX.jpg)`
- **图片数量硬校验**：原文正文图片 N 张 → 译文正文 `![]()` 数量必须 ≥ N×50%。低于此阈值 = 图片丢失，必须补回
- **嵌入视频**：微信公众号不支持 iframe，在对应位置插入 `> 📹 演示视频：[点击查看](url)`

#### 通用

- 结尾必须标注：原始出处名称 + 类型 + 链接
- 格式：
  ```
  *本文内容全部来源于 [来源名] [场合/发布日期] "[环节名/标题]"。*
  *来源：<https://...>*
  ```（`<URL>` 格式单独成行，不用 Markdown 链接语法，防微信吞标点）
- 如果有多个来源（如原始视频 + 中文翻译参考），如实列出

## 🧵 X thread → 模式 C 改写特殊 SOP（X thread 源材料强制，其他源材料跳过）

### 核心差异

模式 C 默认源材料是播客/访谈（长对话，清晰人物+时间+话题弧线），X thread 是碎片化短推文（无明确时间，多 speaker 少，信息密度高但叙事分散）。**两者的最大差异**：播客靠时间戳和对话顺序提供叙事骨架，X thread 靠推文序号但序号不携带逻辑关系——第 3 推文不一定是第 2 推文的论据，可能是新话题开始。

**不处理这层差异，直接把 8-12 条推文直译后套入模式 C 8-10 章骨架** → 章节间逻辑断裂、读起来像"12 条语录的拼贴"——这是用户反馈"语义不通/句式错误/不符合中文表达习惯"的最大根因。

### Step 1.5：X thread 叙事弧线提取（改写前必做）

通读所有推文（在阶段二翻译稿基础上），完成三件事：

1. **识别核心张力**：同 SOP 步骤 3——这场 thread 围绕什么矛盾展开？是产品发布 vs 行业现状？是技术宣言 vs 现实约束？是个人经验 vs 普遍认知？
2. **识别推文间逻辑关系**（4 种角色）：
   - **开篇钩子**：第 1-2 条推文，抛出核心话题或反常识观点
   - **论据展开**：连续 2-5 条推文，分别从不同角度展开核心观点
   - **反驳/深化**：突然转向的推文，可能是回应评论、补充背景、深入一层
   - **收尾**：最后 1-2 条推文，做总结、给行动号召、或留悬念
3. **画推文→叙事角色映射表**（在草稿纸上或注释里）：

```
推文 1：[开篇钩子] - 抛出 X 现象
推文 2：[论据展开] - 数据支持
推文 3：[论据展开] - 案例佐证
推文 4：[反驳/深化] - 回应常见质疑
推文 5：[论据展开] - 更深层原因
推文 6：[收尾] - 行动号召
```

### Step 2.5：推文→章节 合并策略

**原则**：每章 200-500 字（mode C 8-10 节），**不是每条推文 1 章**。X thread 通常 6-15 条推文，目标产出 5-8 章（X 通常比播客访谈章节数少，因为信息密度更高）。

**合并规则**：

| 推文组合 | 章节归属 | 理由 |
|:---|:---|:---|
| 同一话题的连续 2-3 条推文 | 合并为 1 章 | 避免单章字数过少（<150 字） |
| 跨话题转折的推文 | 单独成章 | 转折点是叙事钩子，稀释后失去张力 |
| 引语密集的推文（直接 quote） | 优先独立成章 | 模式 C 核心调性要求"大量直接引语" |
| 含图片的推文 | 保留图片位置（`tweet_index` 对齐） | 配图位置不得跨推文重排（见 SKILL.md 总原则） |
| 重复论点的推文 | 合并到同一章 | 避免冗余，模式 C 要求"信息密度高" |

**输出**：推文→章节映射表（哪几条推文归到哪一章）。这是后续自检的硬性证据。

### Step 3.5：X 特有元素的 mode C 归宿表

按 `ai-translation-guide.md §1.7` 规则处理后，再做以下 mode C 特定归宿决策：

| X 元素 | 翻译稿归宿 | mode C 改写稿归宿 |
|:---|:---|:---|
| hashtag | 按 §1.7.1 删除/保留 | 保留的 hashtag 用术语加注格式（`#Claude` 改为 `Claude` 后加注） |
| emoji | 按 §1.7.2 删除/替换 | 几乎全删，最多保留 1-2 个 `> 💡` 编辑注 |
| 推文编号（"tweet 5/12"）| 翻译稿中删除 | 改写稿绝不出现"他第一条推文""他接着发"等暴露 X 结构的措辞 |
| 引用 | 直接引语 | 整段用 `>` 引用块保留 1-2 条最有力的原推文；其余转为间接引语 |
| 口语化 slang | 按 §1.7.4 弱化 | mode C 必为间接引语（"他用了一个口语化的说法，意思是 X"） |
| 多推文连贯性 | 按 §1.7.5 显式连接 | 改写稿每章首句用"X 说 X 之后""更关键的是""但事实是"等 |

### Step 3.6：图片位置锁定（X thread + 含图片时强制，G6 硬约束）

改写前模型**必须先读** `x_thread_manifest.json` 的 `images`、`videos`、`video_thumbnails` 三个数组，将每个元素的 `tweet_index` 与"推文→章节映射表"（Step 2.5 产出）对齐，输出"图片位置确认表"：

| 章节 | 涵盖推文 (tweet_index 列表) | 本章节包含的图片（来自 manifest） | 插入位置（哪段话之后）|
|:---:|:---|:---|:---|
| 一、[标题] | [0, 1] | images[0] (tweet_index=0), images[1] (tweet_index=1) | 第二段"AI 编程的真正工作流"之后 |
| 二、[标题] | [2] | （无） | — |
| 三、[标题] | [3, 4] | videos[0] (tweet_index=3) → gif 引用 | 引用块"测试就是 prompt"之后 |
| ... | ... | ... | ... |

**强约束**：
- 一张图 `tweet_index` 只能落到"涵盖该 tweet_index 的章节"，**不得跨推文移动**——这是 X 配图最容易出错的地方
- 同一推文多图时，按 `img_index_in_tweet` 顺序排（从 0 起）
- 含视频的章节：`gif_path` 用相对路径 `![描述](images_x_thread/x_video_01.gif)` 引用；如 GIF 转换失败则降级为 `![描述](images_x_thread/x_video_01.mp4)`
- 含 `video_thumbnails` 缩略图的章节：默认不用（视频本身更重要），如改写需要可用 `local_path` 引用
- **该表是硬性 SOP 输出，不得跳过**；缺表 = 改写未完成，对话中需先输出该表再开始撰写正文

### 硬性质控补充

- **来源保真补充**：X thread 源材料允许编辑提炼（每章末尾 `> 💡` 编辑注），但**禁止引入原推文未提及的信息**。如果需要补充上下文（"Alpaca 是 Dubois 在斯坦福期间发起的开源指令微调项目"），必须 ≤30 字括注或 `> 💡` 编辑注。
- **跨推文拼贴禁止（X 模式 C 最常见保真度违规）**：A 推文结论 + B 推文论据，不得改写为"A 导致 B"。X 推文序号相邻不代表逻辑相邻——必须保证改写后的因果/递进/转折关系在原推文中能找到对应。

## 📜 对话转述写作 SOP

1. **通读源材料**：完整阅读原始材料（转录、翻译或博客），不做跳读。**X/Twitter 源材料硬门禁：必须先走 CDP 浏览器提取**——用 CDP `/new?url=` 打开推文后，**先 `/scroll?direction=bottom` 滚到底触发懒加载**（图片不滚动不进 DOM，`querySelectorAll` 返回 `[]` 不代表无图），**等待图片加载完成**，再 `/eval` 提取文本和图片。推荐使用 `scripts/extract_x_thread.py` 一步完成。纯文本方式（WebFetch/Jina）会导致图片静默丢失。此检查在通读前完成，未确认图片 URL 列表前不得进入第 2 步。
2. **提取核心信息**：标注最核心的 5-8 个观点、最有力的直接引语、最有冲击力的数据、最打动人的细节。**如有配图，同步提取每张图的 URL 及其在原文中的位置信息**——每张图必须记录：属于 thread 中第几条推文（`tweet_index`）、该推文的文本内容摘要、该推文中总共几张图。**写文章时，每张图必须放在对应推文内容段落后，不得跨推文重排。** 对 X/Twitter 来源额外检测：检查配图是否为动态图——如果 DOM 中出现 `tweet_video_thumb` 或 `tweet_video` 标签，说明原图是动画 GIF，需下载 MP4 并转换为 GIF（见 SKILL.md 总原则中的 GIF 检测规则）。
3. **确定核心张力**：想清楚这篇文章围绕什么矛盾展开——是速度 vs 安全？解放 vs 颠覆？预测 vs 现实？
4. **选配章节类型**：从章节类型菜单中按需选取 8-10 个章节角色，排定顺序。
5. **撰写导语**：标题已由 SKILL.md 阶段三的标题阻断点完成（按 `references/shared/title-workflow.md` 5 步法生成 + 质控 7 条），确认标题符合模式 C 的"核心人物身份 + 冒号 + 最抓眼球的关键词/金句"公式约束。导语按三段式完整撰写。
6. **逐章撰写**：每章从场景/问题引入，核心观点用直接引语呈现，加数据/细节展开。
7. **三条约法自检**：逐条对照硬性质控规则，确保来源保真、中文自然、来源标注完整。
8. **逐段归源映射（新增，完稿后强制）**：逐章标注每章的"核心论断"和"支撑论据"在源材料中的时间戳/段落位置。同一段对话的完整论述可以组织为叙事弧线；**A 时间戳的结论 + B 时间戳的例证，被改写为"A 导致了 B"的因果叙事 → 必须拆分或标注转折**。检查方法：每章的论断→原文位置对照表，跨话题拼贴的拆开，跨段落拼贴但同话题的标记为合理组织。此步不增加写作负担——完稿后花 3 分钟逐章标一下位置即可
9. **X thread 自检（仅 X 源材料）**：见下方 §X thread 自检清单 9 项。

## 🚫 对话转述禁忌

- 不要扩充源材料中没有的内容——这是第一条也是最重要的一条。
- 不要把翻译腔带进中文——对照翻译指南检查。
- 不要加自己的分析、评价、"这意味着"式推论——你是转述者，不是评论员。
- 不要用"本文将介绍……"这类教科书腔开头。
- 不要写成大白话解释文——那是模式 A 的活。
- 不要写成行业快讯——那是模式 B 的活。
- 不要把 speaker 的观点引申到源材料未涉及的领域。
- 不要遗漏结尾的来源标注行。
- **不要把不同话题段落的素材拼贴为同一因果叙事弧线**——这是模式 C 最常见的保真度违规。A 段落的结论 + B 段落的例证，不得改写为"A 所以 B"。发现跨话题拼贴必须拆分
- **不要在 X thread 改写中暴露 X 结构**（"他第一条推文""他接着发""最后一条推文"）——这些是元叙事，会打破 mode C 的"科技记者整理稿"质感
- **不要保留翻译稿中残留的 hashtag/emoji**（除按 §1.7 决策保留的外）——必须在改写阶段全清
- **不要把 X 推文中的 slang 直接带进 mode C 间接引语**——必须先转为间接引语（"他用了一个口语化的说法"）
- **不要在凝练总结句/金句时自造原文没有的主语**——转述句必须保留原文主语（AI 采用、组织、从业者、初级岗位等具体主体），不得泛化为"系统/生态/格局"等抽象名词；确需概括时"名词+动词"必须是中文自然搭配（资源/专长/人才类蓄水池名词可配"枯竭"，"系统"只配"崩溃/失灵/退化/瓦解"）。**反例**（2026-08-12）：原文 "AI adoption can produce collective expertise depletion"（主语 AI 采用）→ 改写稿写成"系统仍然走向枯竭"（主语自造为"系统"且搭配生硬）→ 修正为"集体专长仍然走向枯竭"

## ✅ 对话转述自检

写完后必须检查：

1. 每句话是否都能在源材料中找到对应？（来源保真）
2. 中文表达是否自然，有无翻译腔？（读出声来，对照翻译指南自查清单）
3. 直接引语是否保留了原话的质感，而不是被转述成间接引语？
4. 来源标注是否完整，包含出处名称、场合和链接？
5. 标题是否有具体的信息量（数据/概念/金句），而不是空洞的形容词堆砌？
6. 各章节是否相对独立、标题本身就有信息量，支持跳读？
7. **源材料含配图时，是否已全部下载到本地并插入文章对应推文段落之后？** 每张图的插入位置是否与源材料的 `tweet_index` 一致？同一推文多张图时顺序是否正确？（X/Twitter 源材料尤其容易遗漏——纯文本获取方式不会报错，但图片静默丢失。）
8. **逐段归源映射已完成？** 每章的核心论断和支撑论据是否来自源材料中同一话题段落？有无跨话题拼贴的因果关系？跨段落但同话题的标记为合理组织即可
8.5. **直接引语逐条归源已核对？** 文章中所有用引号 `""` 包裹的直接引语，是否每一条都能在源材料中找到逐字对应？合成句/总结句/作者推断——即使忠实地概括了 speaker 的立场——**禁止**使用引号包装成原话。判断方法：遮住引号，这句话是你写的还是 speaker 说的？你说的一律去掉引号改为编辑叙述。**反例**（2026-07-21）："我对 AI 技术极度乐观。我对 AI 模型公司极度悲观。这两个判断不矛盾。"——源材料无此原话，是作者合成句包装为引号。
9. **X thread 自检（仅 X 源材料强制）**：
   - 9.1 推文→章节映射表是否已生成？每章至少 200 字？
   - 9.2 章节数是否在 5-8 节（X 通常比播客访谈章节数少）？
   - 9.3 hashtag/emoji 是否按 §1.7 归宿表处理？（残留数 = 0 或仅保留的术语加注）
   - 9.4 是否避免了 X 结构暴露？（"第一条推文""接着发"等措辞 = 0）
   - 9.5 是否避免了跨推文拼贴的因果叙事？A 推文结论 + B 推文论据改写为"A 导致 B" = 0 处
   - 9.6 章节首句是否用了显式中文连接词？（每章首句包含"X 之后""更关键的是""但事实是"等）
   - 9.7 slang 是否全部转为间接引语？（`lol` `tbh` `this is wild` 等裸用 = 0 处）
   - 9.8 broken sentence 修复是否在翻译稿中已处理？（无孤立短语直译）
   - 9.9 是否对修改稿执行过 1 段朗读抽查（C3 快路径即可）？
   - 9.10 **图片 `tweet_index` 与插入位置章节已对齐（G6 硬约束）**？逐项核对：manifest 中每张图/视频的 `tweet_index` 是否落在"该章节涵盖推文列表"中？跨推文移动数 = 0
   - 9.11 **图片引用路径与 manifest `local_path` 一致（G8 硬约束）**？改写稿中所有 `![](...)` 引用的相对路径都能在 manifest 的 `images`/`videos`/`video_thumbnails` 数组的 `local_path` 中找到；找不到的引用 = 0；改写稿自创的、未在 manifest 出现的图片引用 = 0
   - 9.12 **C2 扫描 4（名词堆叠）误报已排除（G9 硬约束）**？逐项核查扫描 4 的每个触发：是被动语态直译的冗余名词堆 → 改写；是架构性长名词短语或中文口语自然停顿 → 标注"误报，保留"。**禁止为清零扫描器而牺牲架构语感**——上一轮四轮审校中此问题导致核心系统设计语句被过度简化（"执行任务的模型…"→"干活的模型…"），被打回重写。附带检查：全文无 L3 自媒体/菜市场口语渗入（`炸出圈`、`干活`、`挂了没`、`有意见就改`）
   - 9.13 **改写阶段自产比喻语域通胀已排除（G10 硬约束）**？逐段扫描含画面感的动词/名词比喻——这个比喻在源材料里有对应吗？没有 → 改写者自产比喻 → 问一句：这是"技术分享会上会说的话"吗？不是 → 降为直述。**反例**（2026-07-15）："停下拇指""刹一脚""矛头只对准"均为源材料无对应、改写者自产的 L3 比喻，全部打回。附带检查：含隐喻通胀的句子是否为改写时新增？→ 是 → 降级或删除
   - 9.14 **术语链完整性已确认（G11 硬约束）**？全文搜索所有英文技术术语的每次出现——每个术语的**首次出现**必须是 `中文描述（English）` 格式。任一中文描述在另一章节裸用 → 回到该章节首段补 bilingual。**反例**（2026-07-15）："具备自主行动能力"在 §2 首现时无 `（Agentic）` 标注，"Agentic AI"在 §5 裸用 → 术语链断裂，两处概念无法关联。修复：§2 首现补为"具备自主行动能力（Agentic）"，§5 "Agentic AI"继承
   - 9.15 **商业/行政时间窗口表达已核查（G12 硬约束）**？全文搜索时间+数字+行政动作的组合（如"N 天+提交/发布/申报"）。原文为 `up to N days before release` 等窗口型表达 → 中文必须使用"留出最高 N 天的窗口期"，**禁止**使用"最多 N 天"（产生 deadline 上限歧义）。**反例**（2026-07-15）："up to 30 days before release"→"最多 30 天提交评估"（读者第一反应：审查时间上限 30 天）→ 修正为"留出最高 30 天的窗口期向该机构提交评估申请"
   - 9.16 **人称代词人物识别已确认（G13 硬约束）**？全文搜索 `用它` / `用她` / `它说` / `它认为` / `它指出` → 指代对象是人物 → 改为 `用他`（或按性别用 `用她`）。两字均合法汉字，逃过拼写检查和朗读（大脑自动纠正），只能靠机械搜索。**反例**（2026-07-17）："用它自己的话说——"指代 Satya Nadella → 应为"用他自己的话说"，4 轮审校全部漏过

   - 9.18 **搜索片段重建源材料的事实失真预检已完成（G15 硬约束）**？当企业安全策略阻断 PDF/CDP 直连、源材料从搜索引擎片段交叉验证重建时，以下三类事实完稿后逐项回溯搜索原文验证——①**时间精度**：搜索片段常省略或压缩时间粒度，"三天后"可能是从"迅速加入"脑补的；②**法律动作定性**：搜索片段普遍混淆"起诉""致信指控""调查""罚款"，每个法律动词必须确认动作发出者和接收者；③**数字与事件的归属关系**：数字可能正确但附着的法律/商业动作可能错位。**反例**（2026-07-27）：Forbes 报道"in a single day"→我写成"三天后"；Anthropic 致信参议院→我写成"起诉阿里巴巴"
