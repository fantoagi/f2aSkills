## 一、核心翻译原则

### 1. 精准还原优先（Fidelity First）
- **不增删、不概括、不主观润色**：严格对应原文段落结构、逻辑递进与信息密度。
- **技术细节零妥协**：架构设计、数据流向、模型行为、实验结论等必须 100% 准确传递。
- **语气与立场保持一致**：原文的批判性、前瞻性或克制表述需完整保留，不中性化或情绪化。

### 2. 普适可读导向（General Audience Ready）
- 面向泛 AI 读者，技术概念需**准确但易懂**。避免学术化长句，可用符合中文习惯的短句重组，但绝不改变原意。
- 复杂机制（如 RAG 检索链、Agent 规划循环）若原文已解释，译文需保持同等解释粒度；若原文默认读者具备基础认知，译文不额外补充背景。

### 3. 术语双语策略（Hybrid Terminology）
- **业内高度共识的英文词直接保留**：不强行翻译已固化且广泛使用的英文名词/缩写。
- **首次出现可加注**：采用 `英文（中文释义）` 或 `中文（英文）` 格式，后续统一使用最简形式。
- **语境决定译法**：同一词在不同上下文（如 `Memory` 在模型上下文 vs 数据库缓存）需采用对应准确表述。

### 4. 代码块与 Prompt 全量原样保留原则（Do Not Touch the Code）
- **最高优先级**：所有 fenced code block、inline code、CLI 命令、JSON/YAML、API 字段、Prompt/System Instruction/Few-shot 示例，必须逐字原样保留。
- **禁止操作**：不得翻译、重排、清洗、补全、格式化或"好心修复"代码块内容；不得清理 JSON/YAML 键名、尾部空格或命令参数。
- **疑似错误处理**：若原文代码疑似有错误，只能在代码块后用中文编辑注说明，不得改动代码块本体。
  - *格式要求*：`[原文代码块逐字保留]` + 代码块后单独中文说明（如需要）

### 5. 极客科普短句重构原则（Punchy & Conversational Tone）

**⚠️ 模式豁免**：本规则仅适用于源材料为 X/Twitter/Substack 短线程/独立主理人博客的场景。**正式报告、技术架构文档、论文/评测、模式 C（对话转述）的播客/访谈/长文源材料不适用 Punchy Style**——这些材料必须保留原文节奏、解释粒度和论证链条，不得压缩为断言式短句。判断标准：源材料单篇超过 1500 英文词或明显为访谈/技术文 → 自动跳过本条全部子规则。

当原文属于 X/Substack/独立主理人风格的短句、断言式、要点科普内容时，严禁点对点直译，必须采用以下策略还原”顿挫感”与”对话感”：
- **名词动化/场景补全**：英文常裸用名词列举（如 `use for: code, facts`），中文必须补全为“动词+名词”或明确业务场景（如 `适用于：代码生成、事实检索`）。
- **AI 拟人动作加引号**：英文用人类动作描述 AI 机制（如 `look up, think, memory`）时，中文保留拟人动词但**必须加双引号**以示技术严谨（如 `让模型先"查证"再回答`、`留出"思考"空间`）。
- **断言语气还原**：英文利用短句结构产生的断言感时，中文可用 `正是`、`其实`、`核心洞察` 等词还原同等强度，避免干瘪；但不得超过原文强度（如 `This single idea unlocked...` → `正是这一个构想，直接开启了...`）。
- **抽象概念具象化（Noun Anchoring）**：将泛指的状态/名词转化为中文互联网/AI圈习惯的认知载体（如 `mental models` → `核心思维框架`；`That gap is your edge` → `这种认知差，正是你的竞争优势`）。
- **语气不越界**：中文本地化只允许重构表达，不允许增强原文没有的情绪、判断、确定性或立场。若原文克制，译文必须克制；若原文只是猜测，译文不得写成结论。

### 6. 研发语境对齐原则（Engineering Context Alignment）
面向开发者指南、配置文档、架构分析时，英文常用生活化通用词描述技术状态。必须映射为中文研发圈标准表述，严禁字面直译：
- **动词匹配操作介质**：UI 面板用“切换/勾选”，JSON/代码配置用“设为/改为/切到”，物理硬件才用“翻转/拨动”。
- **状态词匹配系统语境**：缓存/上下文/服务器场景的 `cold/warm` 译为`冷启动/预热`；API/负载场景的 `bursts/spikes` 译为`突发流量/瞬时高并发`。
- **反同义反复**：英文定语从句表状态（如 `candidates that didn't make the cut`）中文需压缩为“状态词+实体”（`落选配置项`），杜绝“没入选的候选”等冗余表达。

> 完整术语表 → `references/glossary-ai.md`

### 7. X/Twitter 源材料翻译特殊规则（X thread 强制，其他源材料跳过）

**触发条件**：源材料为 X/Twitter thread（不论推文数量多少）。X thread 不同于常规英文材料——碎片化、口语化、含 hashtag/emoji/broken sentence——必须按本节规则做专项处理后再进入改写阶段。

#### 7.1 hashtag 处理决策树

按 hashtag 类型分别处理：

| hashtag 类型 | 案例 | 处理 |
|:---|:---|:---|
| 核心专名/产品/公司 | `#Claude` `#OpenAI` `#DeepSeek` | 保留为术语加注（`#Claude` 保留原样） |
| 行业常用英文缩写 | `#AI` `#LLM` `#RAG` | 保留 |
| 情绪/行动号召 | `#GameChanger` `#MustRead` `#Thread` | 删除 |
| 中文里已是热词 | `#VibeCoding`（见 glossary §7） | 首次出现保留为术语，第二次起删除 |
| 多 hashtag 同一推文 | `#AI #LLM #FutureOfWork` | 最多保留 1-2 个核心（专名+行业缩写），其余删除 |

**为什么**：hashtag 在 X 平台是"分类标签"，但在 mode C 长文中无功能。中文读者看到 `#AI` 在段落中突兀，破坏阅读节奏。`#Claude` 保留因为它是产品名/术语，本身在 mode C 中要加注。

#### 7.2 emoji 处理决策树

| emoji 类型 | 案例 | 处理 |
|:---|:---|:---|
| 标点性 emoji（句末强调） | 句末的 `🔥` `💯` `🚀` `👏` | 删除（中文用标点+语气词替代） |
| 信息性 emoji | `⚠️` `✅` `❌` `💡` | 替换为中文：`⚠️` → `> ⚠️` 编辑注块；`✅` `❌` → "是"/"不是"；`💡` → 删除（模式 C 用 `> 💡` 编辑注） |
| 视觉性 emoji（描述产品/概念） | `🚀` 在 "🚀 Product launch" | 删除 |
| 引用性 emoji（`🧵` 标识 thread） | `🧵` `👇` 引导阅读 | 删除（thread 结构在 mode C 中已被章节结构替代） |

**为什么**：mode C 调性要求克制（参考 mode-c.md §核心调性 4："中文口语化但正式"）。emoji 保留破坏克制感，读者会觉得"这不是公众号文章而是朋友圈"。

#### 7.3 broken sentence 修复（最常见翻译陷阱）

X 推文常省略主语、连词、定冠词（"probably 80% by 2026"），直译后是孤立短语。**翻译时必须补全主谓结构 + 显式中文连接**。

| ❌ 直译 | ✅ 修复 |
|:---|:---|
| Probably 80% by 2026. | 业界预测，到 2026 年这一比例可能达到 80%。 |
| 5x faster, 1/10 cost. | 处理速度提升 5 倍，成本降至原来的十分之一。 |
| Same model, different prompt. | 即便使用同一模型，不同的 prompt 也会带来截然不同的结果。 |
| Going to be huge. | （将）带来巨大影响。 |

**修复规则**：
- 缺主语 → 补主语（"模型""团队""业界""他"等）
- 缺动词 → 补动词
- 缺连词 → 补"因此""但""而"等显式逻辑
- 缺时间/条件 → 补"到 X 年""在 X 条件下"

#### 7.4 slang/口语填充词处理

| 类型 | 案例 | 处理 |
|:---|:---|:---|
| 缩略 slang | `lol` `tbh` `imo` `ngl` `fwiw` | 删除（无声翻译） |
| 强调 slang | `this is wild` `no cap` `fr fr` `lowkey` `highkey` | mode C 中转为间接引语：`"他用了一个口语化的说法，意思是 X"` 或 `据他本人描述，X 超出了他的预期` |
| 网络俚语 | `based` `cringe` `mid` `slay` | mode C 几乎全删；如必要转为"很棒""很尴尬""平庸""表现惊艳"等 |
| 重复强调 | `very very` `really really` | 删除冗余一次 |

**为什么**：mode C 要求"科技记者整理稿"质感，记者转述不会保留 `lol` `tbh`。这些 slang 在中文里没有对应物，强译反而制造翻译腔。

#### 7.5 多推文连贯性强制（X thread 转 mode C 长文的命门）

X thread 多条推文间常隐含逻辑（因果/递进/转折/举例），直译后每条推文独立成段、互不相关。**翻译时必须在每段开头用中文显式连接词**：

| 原文隐含逻辑 | 中文显式连接词（首句） |
|:---|:---|
| 因果 | "之所以……""正因如此""这意味着" |
| 递进 | "更进一步""更关键的是""不仅如此" |
| 转折 | "但事实是""然而""与之相反" |
| 举例 | "一个典型案例是""比如""他举了个例子" |
| 总分 | "他分了几点说""他强调了几个维度" |
| 总结 | "一句话""总之""他最后总结" |

**为什么**：X 平台读者能从 thread 序号和"👇"等线索感知叙事，但中文长文读者没有这些线索。必须把隐含逻辑翻译为显式中文连接，否则章节间断裂。

#### 7.6 §1.7 规则触发的强制标注

翻译完成后，**必须在阶段二 E 后校验表前**输出 `§1.7 触发清单`：

```
§1.7.1 hashtag：触发 N 处（删除 X / 保留 Y）
§1.7.2 emoji：触发 N 处（删除 X / 替换 Y）
§1.7.3 broken sentence：触发 N 处
§1.7.4 slang：触发 N 处
§1.7.5 多推文连贯性：触发 N 处（每段首句显式连接）
```

触发计数为 0 → 标注"0，本任务无 X 特有元素或全部已按默认处理"。

## 二、标准化工作流

### 阶段 0：轻审计分流（所有英文源材料强制）

英文源材料进入翻译前，先判断风险等级并在对话中输出轻审计闸门：风险等级、核心术语清单、代码块清单、3 个高风险句校验、是否先翻译再改写。不得跳过该闸门直接输出正文。

**低风险材料**：普通产品发布、短新闻、无代码/API/评测/长访谈的短英文材料。默认走轻审计。

**高风险材料（任一命中即升级完整审计）**：长访谈/播客/模式 C 对话转述、技术架构、API/JSON/YAML/代码/Prompt、X/Twitter thread、论文/评测/benchmark、原文超过 600 英文词（见 SKILL.md 阶段 1.5 分流判定）。高风险材料必须执行阶段 1-3 的完整流程。

### 阶段 1：预处理（5-10 分钟）
- [ ] 通读全文，高亮核心 AI 术语，对照 `glossary-ai.md` 确定保留词/译法/加注项
- [ ] 扫描专有名词（TerminalBench, Ralph Loop 等），确定加注方式
- [ ] **领域黑话识别**：当原文涉及编译器/开发工具/Agent 编排等领域时，扫描是否存在"中文有通用译法但领域内有标准黑话"的术语。典型例子：`bootstrapping` 在编译器语境 = "自举"（非"引导"或"递归"）；`worktree` 在 Git 语境 = 保留 Worktree（非"工作树"）。对照 `glossary-ai.md` §9 开发者工具域确认
- [ ] **ASR 源材料专名校验（播客/访谈转录强制）**：从转录稿中提取所有疑似产品名/公司名/工具名，逐一确认"市面上有这个产品吗？"。ASR 极易将 `Claude` 误识为 `Cloud`、将连读误合并为新词（如 `Perplexity, computer use` → `Perplexity Computer`）。校验不通过的不采信，对照上下文修正。**通过后追加归属校验：每个产品名→确认归属公司（如 Cowork→Anthropic 非 OpenAI、Codex→OpenAI 非 Anthropic），对照原文语境交叉验证。** 此步为纯机械操作——逐词过，不需要领域直觉
- [ ] 标记核心判断句（定义/结论/警示/数据驱动），对照 quickref 加粗标准
- [ ] 识别原文图表/代码/引用块——代码块/Prompt/API/CLI 必须逐字原样保留
- [ ] 判断文章基调（技术架构/商业战略/产品发布/投资分析），调整译法颗粒度
- [ ] 标记研发语境高频词（cold/warm/flip/bursts/kill/make the cut 等），预判映射策略
- [ ] 读 `translation-principles.md` 四条原则（含原则 D 语域分级），标记原文中可能触发每条原则的段落

### 阶段 2：翻译执行（轻审计默认，高风险分块验证）

**分块策略（高风险材料强制执行）**

高风险材料不采用全文逐段线性翻译，而是拆分为逻辑独立的 chunk 处理，避免长上下文导致后半段自问规则衰减。低风险材料可线性翻译，但仍必须完成轻审计闸门和后校验摘要。

**拆分规则**：
- 按原文的逻辑章节边界切分（`##` / `###` 级别），禁止在段落中间切断
- 每块目标大小 1200-1800 字（英文），不得少于 800 字（太短浪费拆分开销）
- 相邻章节如总字数不足 1200 可合并为一组
- 拆分后生成 chunk 清单：`Chunk 1: §§1-3 (1500 字) / Chunk 2: §§4-6 (1600 字) / Chunk 3: §§7-8 (1200 字)`

**分块执行流程**：
```
Chunk 1 → 翻译（三条原则逐句内化 + 🔴5 条硬事实自检） → ✅ → 记录本块术语使用清单
Chunk 2 → 注入 Chunk 1 术语清单 → 翻译 → ✅
Chunk 3 → 注入 Chunk 1+2 术语清单 → 翻译 → ✅
    ↓
合并 → 跨块术语一致性检查 + 母语者朗读 3 段兜底 + 后校验
    ↓
交付
```

每个 chunk 翻译完成后立即执行自检。不在合并后再补检——那时自检规则已被更大的合并上下文稀释。

**分块术语传导**：每翻译完一个 chunk，输出本块**实际使用的**术语清单（不只是阶段 1 的计划清单，而是翻译中实际落实的译法），递交给下一块。格式缩至最少：
```
Chunk 1 术语传导：`orchestration`→编排 | `KV Cache`→KV Cache（键值缓存，已加注） | `harness`→Harness（调度框架，已加注）
```
下一块开始翻译前，此传导行注入 prompt 最前面。

**反例注入（每 chunk 强制执行）**：每 chunk 翻译开始前，注入以下禁忌规则到翻译 prompt 的最前面。**注入分两层：确定性基座（必注，不依赖 LLM 自选）+ 上下文增量（LLM 按 chunk 特征追加）。**

**确定性基座（每 chunk 必注，不跳过）**——以下 10 条是已验证的跨内容类型高频错误，LLM 对它们的盲区是系统性的：

```
⚠️ 本段基座禁忌：
1) 英文句式→中文："This is why"→不用"这就是为什么"，用"正因如此/所以"
2) 被动→主动：删除冗余"被/进行/作出/加以"
3) 空间动词+抽象宾语："穿过/走进/踏入"+研究/对话/论文→"贯穿/面对/进入"
4) 万能动词"做/搞/给"+技术产物→"写代码/构建系统/交由…处理"
5) "的"≥3次→拆句；主语-谓语≥15字→调语序
6) 语域分级（原则 D）：Mode C 锁定 L2 专业口语——禁止菜市场用语（"零头/便宜货"）、游戏/体育俗语（"下场打球/送人头"）、拟人化情绪（"手太松了/脑子进水"）。像技术分享会说话，不像大排档吹牛。**语域校准硬规则**：当原文本身是口语/俚语风格（如 X Article 用"babysitting""burns you""flex"），中文必须拉回 L2——"babysitting"→"手动兜底"而非"当保姆"，"burns you"→"误导你"而非"坑你"，"flex"→"展示实力"而非"炫耀"。判断方法：遮住原文读中文，如果像朋友在微信聊天→语域过低→拉回
7) 领域黑话：chunk 中出现 bootstrapping/自写自语境→用"自举"非"递归"；worktree/commit/hook 等 Git 术语→保留英文（详见 glossary §9）
8) 词性边界（glossary §10）：Orchestration=编排（机制）非"编排者"（角色）；Harness=运行框架非"调度"（调度=Scheduling）
9) 排版规范（glossary §11）：中文引号用全角""不用半角""；中文括号用全角（）；破折号用——不用--；专有名词首字母大写（Git/GitHub/Token）
10) 修饰词增量=语气越界：原文 "the gap" 只能译为"鸿沟"，不能加"认知"变成"认知鸿沟"。每添加一个原文没有的形容词/限定词，都是对读者判断的干预。检查方法：遮住原文，把中文译文每个形容词/限定词逐一问"原文有吗？"→没有→删。
    **⚠️ 例外（允许添加/替换，不视为越界）**：
    - **消歧**：概念术语中文首次出现可能导致歧义时（如"理解债务"语境下"鸿沟"→"认知鸿沟"可帮助读者定位）
    - **中文表达自然度**：直译后中文搭配不自然、读起来像翻译腔时，允许替换为更地道的中文表达（如"接线"→"打通链路"、"机器"→"引擎"）
    - **隐喻对等映射**（原则 E）：英文隐喻直译后中文画面感碎裂时，替换为中文等效隐喻或直述
    - 以上三类添加/替换必须逐案论证，不可泛化。判断标准：**遮住原文读中文，这句话像中文母语者写的吗？** 不像→允许调整至像为止
    - **常见搭配陷阱**（直接替换，不需要论证）：
      - "free tier" → "免费版"（不是"免费层"）
      - "$20" → "20 美元"（不保留 $ 符号）
      - "paste your life into a chat box" → "反复向 AI 复述自己"（不是"把生活粘贴进聊天框"）
      - "dialect"（tech 语境）→ "语法/写法"（不是"方言"）
      - "locked in"（vendor lock-in）→ "不被平台绑死"（不是"不会被锁定"）
```

**上下文增量（每 chunk 按特征追加 2-3 条）**——从 `translation-quickref.md` 原则 A/B 和 `glossary-ai.md` §4/§6 中，按当前 chunk 的**词汇特征**（非 LLM 的主观"最可能"判断，而是机械匹配：chunk 中出现 `labs` → 注入"labs→不用实验室，用巨头"；chunk 中出现 `horizontal` → 注入"horizontal→不用横向，用通用型"）选取。

格式：`⚠️ 本段增量禁忌：1) "come for"→不用"扑向"，用"抢占/吃下"（chunk 含 market/compete 语义） 2) …`

目的：确定性基座保证最低质量底线（最常见的 5 类错误被 100% 拦截），上下文增量处理 chunk 特定风险。两者都在 LLM 注意力最优的前 200 token 窗口内加载。

**X/Twitter thread 源材料强制补充**：除上述两层外，必须额外注入以下**确定性 X 基座**（3 条，不依赖 LLM 自选）：
```
⚠️ X 基座禁忌：
1) broken sentence→补主谓结构（"Probably 80% by 2026"→"到 2026 年这一比例可能达到 80%"）
2) slang→间接引语（"this is wild"→"据他描述，这超出了他的预期"）
3) 多推文→段首显式连接词（"之所以/更关键的是/但事实是"）
```

再按 chunk 中的 X 特有元素，从 `examples/translation/punchy-style-cases.md` 机械匹配追加 1-2 条（chunk 含名词裸用→注入场景补全规则；chunk 含数字+时间→注入高保真锚点规则）。

**翻译执行原则**：
-1. **五条原则内化（最高优先级）**：翻译每句前先过 `translation-principles.md` 五条判断口诀——A. 结构脱钩了吗？B. 搭配成组了吗？C. 短句密度够了吗？D. 语域在 L2 吗？E. 隐喻对等了吗？五条原则覆盖翻译腔句式、搭配越界、结构隐喻、介词框架、代词堆砌、长定语、被动冗余、语域漂移、隐喻替换、研发语境映射等所有语感维度。不需要逐条记忆 130 条规则。
0. **术语映射清单注入**：翻译每段/每块前，必须先从阶段 1 生成的术语映射清单中提取本段出现的术语条目，注入到当前段落的翻译 prompt 最前面。清单格式：`| 原文术语 | 本文统一译法 | 首次段落 | 加注？ |`。目的是让 LLM 在翻译时的术语选择决策发生在前 200 token 的注意力窗口内，而不是依赖"记住 3000 token 前的选择"。清单每段只需 2-5 行（仅注入本段涉及的术语）。
1. **逻辑段落严格对应，视觉段落允许微调**：不跨逻辑层级合并段落；但若英文单段超过 250 字且包含明显的逻辑转折（如 However, Furthermore），允许在中文译文中拆分为 2-3 个视觉段落，以缓解移动端阅读压迫感。
2. 逻辑显式化：英文隐含的 because/which/while 用中文`因/故/而/尽管`显式连接，复杂因果用`——`强化
3. 技术保真：模型能力、数据流向、架构边界等描述严格逐字校准
4. **可读性优化**（**忠实翻译模式也适用**）：被动转主动、长句拆为短句、抽象名词具象化、补缺失的字、量词具体化、动宾搭配优化——只要事实/数字/立场不变，可做 1-3 词局部调整；不做整句重组。删除冗余`被/进行/作出`
5. 术语一致：全文同一概念译法/保留形式绝对统一（对照 `glossary-ai.md`）
6. 核心判断句加粗（标准见 `translation-quickref.md` 加粗标准）
7. 口语化隐喻替换为专业等效表述（参考 `translation-quickref.md` 隐喻表）
8. **排版铁律（盘古之白）**：中英文混排时，中文与英文单词、中文与阿拉伯数字之间，**必须增加半角空格**。

**专有名词加注拦截机制**：
- 预处理时填入「加注清单」的术语，执行阶段必须逐项确认首次出现已加注
- 未加注项标红，阶段 3 校验时强制拦截，不得交付

**代码块与 Prompt 原样保留执行细则**：
- 原文展示的代码块、Prompt、System Instruction、Few-shot、CLI 命令、JSON/YAML、API 字段必须完整保留英文原版
- 置于独立代码块中，**禁止**在代码块内添加中文翻译、格式化、清洗或补全
- 可在代码块下方用中文注释解释核心逻辑（如"// 此 prompt 用于让 Claude 先提问再执行"），但不得改动代码块本体

**执行时连续自问（先过五条原则，再查机械项）：**

每句翻译时先过 `translation-principles.md` 三条原则的判断口诀，然后仅对以下不可由原则推导的硬事实执行逐项检查：

| 优先级 | # | 自问项 | 触发条件 |
|:---|:---|:---|:---|
| 🔴 | 1 | 该术语是固化英文词吗？→ 保留/查 glossary | **每段必检** |
| 🔴 | 2 | 这是专有名词且首次出现吗？→ `英文（中文释义）` 加注 | **每段必检**（首次后跳过） |
| 🔴 | 3 | 原文数字/百分比完整保留了吗？ | **每段必检** |
| 🔴 | 4 | **高保真锚点**：原文同时出现具体数字 + 具体物体 + 时间窗口的组合时（`$1000/single task`、`10 lunches/10 seconds`），三项全部原样保留，未替换意象、未压缩时间关系？ | 遇数字+物体+时间组合触发 |
| 🔴 | 5 | 代码块/Prompt/API/CLI 逐字原样保留，未翻译、未清洗、未重排？ | 遇代码块触发 |
| 🔴 | 6 | 核心判断句加粗了吗？ | **每段必检** |
| 🟡 | 7 | 反引号成对？代码块语言标签已标注？ | 遇代码块触发 |
| 🟡 | 8 | 语气未越界？（中文本地化不增强原文没有的情绪/判断/确定性） | 遇断言/结语句触发 |
| 🟢 | 9 | 盘古之白：中文+英文/数字间有半角空格？ | 每 500 字自检 1 次 |

> **分层逻辑**：🔴 为不可逆错误（术语误译/数字偏差/代码损坏），漏检代价高，逐段强制执行。🟡 为硬事实但可后校验修复。🟢 为格式化，归入后校验。

> **原则覆盖的范围（不再逐条自问）**：翻译腔句式拦截、搭配边界越界、结构隐喻直译、介词框架照搬、名词句缺失主谓、代词堆砌、长定语拆分、被动冗余、隐喻替换、Punchy 语气还原、研发语境映射——这些都由 `translation-principles.md` 三条原则在翻译时覆盖。见原则文件末的自我检查口诀。

**交付前兜底（翻译完成必做）**：
执行 `translation-principles.md` 末的三道机械扫描——结构→搭配→密度。不靠"读起来顺不顺"的直觉，靠机械条件触发。所有标题/小标题 + 全文逐句过。

**遇到不确定时：**
- 术语：查 `glossary-ai.md`，若无则查阅主流 AI 媒体或官方中文文档
- 结构/搭配/密度：回到 `translation-principles.md` 三条原则的判断口诀
- 模式替换：查 `translation-quickref.md` 对应原则分组下的速查表
- 语境：战略/商业分析术语可适当口语化，技术架构保持严谨
- 保留词：犹豫时默认保留英文+首次加注

### 阶段 3：后校验 + 复盘（质量门禁 + 反馈闭环）

**轻审计门禁检查**：低风险材料至少输出 checklist 摘要：风险等级、术语、代码块原样、3 个高风险句、先翻译再改写、语气不越界、母语者朗读 3 段无卡顿。

**人工门禁检查**：高风险材料逐项完成 `references/translation-checklist.md` 全部勾选。

**回译验证（所有材料强制，不可跳过）：**

翻译完成、后校验通过后，执行以下回译验证。本步骤不依赖翻译过程的任何中间产物——只对比最终中文译文与英文原文的信息等价性。

1. 从中文译文中选取段落。**分层抽样替代随机抽样**（反"静默事实漂移"——随机抽样可能全落在过渡性段落，漏掉核心论断章）：
   - **规则**：原文每个主章节（`##` / `###` 级别）至少选 **1 段**，优先选该章中含核心论断、数据、技术因果链的段落
   - **总量**：低风险材料覆盖所有主章节（若原文仅 2-3 章则每章 1-2 段，总量 ≥3 段）；高风险材料覆盖所有主章节 + 额外从最核心的 2 个章节各多抽 1 段（总量 ≥5 段）
   - **举例**：原文有 4 个主章节 → 低风险每章 1 段 = 4 段；高风险核心 2 章各 2 段 + 其余各 1 段 = 6 段
2. 将选中的中文段落回译为英文
3. 将回译英文与原文英文逐段对比，检查以下维度：
   - 事实断言：是否缺失、新增或改变？
   - 数字/百分比/时间：是否精确一致？
   - 因果/条件/转折关系：逻辑方向是否保持？
   - 技术细节：架构、数据流、模型行为描述是否等价？
4. 输出回译验证表：

| # | 原文段落位置 | 所属章节 | 回译一致性 | 差异说明 |
|---|------------|---------|:---:|------|
| 1 | §X（约第Y段） | 第N章 | ✅/⚠️/🔴 | [无差异 / 列出具体差异] |
| ... | ... | ... | ... | ... |

- ✅ = 回译与原文信息等价
- ⚠️ = 轻微差异，不影响核心认知（如措辞调整）
- 🔴 = 事实性差异，必须回溯原文段落修复后重新验证

任一 🔴 → 定位对应中文段落 → 对照原文重新翻译 → 再次回译验证直到消除 🔴。
全部 ✅/⚠️ → 回译验证通过，可进入下一阶段。

**反馈闭环：**
- [ ] 记录”不确定/查资料”的术语，登记至 `glossary-ai.md` 待定区
- [ ] 摘录 1-2 个优化前后对比片段存入 `examples/translation/`
- [ ] 发现新搭配越界/结构脱钩案例→补入 `translation-principles.md` 对应原则（不加新规则，只加案例）
- [ ] 标注流程中卡点/模糊点，月初复查对齐

**执行疲劳防护（短/中文强制，长文的分块流水线天然覆盖）：**
- 原文 ≤2000 字（不走分块，全文线性翻译）：每完成约 1000 字翻译执行一次"中段自检"——随机抽取 1 个已翻译段落，逐项回溯 3 条 🔴 高危自问（数字保留？专有名词加注？判断句加粗？）。任一失败 → 回溯该段落所在章节重新翻译。
- 原文 >2000 字（分块流水线）：每个 chunk 翻译完毕时的自检已天然阻断标准衰减。合并阶段额外关注 chunk 边界处（前后两块的首尾段）的术语一致性和语气衔接。
> 操作路径：打开 `glossary-ai.md` → 滚动至第 8 节"术语争议历史" → 按表格格式追加一行

> **翻译心法**
> AI 行业内容的翻译，**精准不是字字对应，而是行业语言习惯与信息密度的双重还原**。
>
> 面对泛读者：
> - 不降低技术准确性，不堆砌学术黑话
> - 不强行汉化固化英文词，不制造理解摩擦
> - 用中文的流畅承载英文的严谨
>
> 每完成一段自问：
> *"这段译文是否让中文读者获得了与英文读者完全相同的技术认知与商业判断？"*
>
> 若答案是肯定的，则翻译成功。
