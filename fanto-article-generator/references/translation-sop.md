# 翻译 SOP（标准作业程序）

> **使用时机**：任何模式（A/B/C/D）的英文源材料翻译任务开干前必读。
> **定位**：**workflow 编排器**——不重复各 reference 的具体规则，只做"何时用哪个 reference"的串联 + 软错层的硬规则补充（其他 reference 都在硬错层）。
> **加载关系**：本文件是入口。读完本文件后按需加载：
> - 硬错层（机械条件）：`translation-checklist.md` / `translation-quickref.md` / `source-inventory-protocol.md` / `ai-translation-guide.md`
> - 软错层（语义判断）：`editor-polish-checklist.md` / `cross-cultural-terms.md` / `glossary-ai.md` / `media-voice-profiles.md`
> - 模式规则：`mode-a.md` / `mode-b.md` / `mode-c.md` / `mode-d.md` / `shared/title-workflow.md`
> - 案例库：`examples/translation/README.md`（8 个分类案例）
> - 跨工程硬规则：`SKILL.md` 5 阶段硬阻断 + 12 项闸门

---

## 〇、元原则：软错层 vs 硬错层

| 层 | 工具 | 触发条件 | 失败代价 |
|---|---|---|---|
| **软错层**（语义判断）| 资深编辑目检 / 案例对照 / 跨文化术语查表 | 翻译腔 / 网络烂梗 / 抽象直译 / 动词介质错配 | 阅读体验差、可被资深读者一眼识别为 AI 稿 |
| **硬错层**（机械条件）| grep / C2 扫描 / L0 源 dump / preflight | 数字幻觉 / 漏译 / 篡改 / 代码损坏 / 跨术语不一致 | 整篇返工 / 公关事故 |

**本 SOP 同时管两层**——软错层补充 skill 现有规则的盲区，硬错层作为每阶段的"通过条件"硬阻断。

## 一、阶段 0：模式 + 风险分级（翻译前必做）

### 1.1 模式判定

按 `SKILL.md` §模式选择 触发词分流：

| 模式 | 触发词 | 适用场景 |
|---|---|---|
| A | 番外篇、系列文章、fanto 风格 | 自有专栏长文 |
| B | 行业快讯、像机器之心 | 产品发布/融资 |
| C | 对话转述、播客、访谈、演讲、**转译** | 行业访谈/播客/X 内容转述 |
| D | 学习笔记、试用体验、踩坑 | 个人视角认知重构 |
| R | 微调、改一下、修改、润色 | 已成稿的单点/多点修改，不跑翻译管线 |

**Mode R 短路**：命中 Mode R 时，直接跳转 `references/mode-revision.md` 执行，**跳过本 SOP 全部阶段**。

**意图优先级冲突时**（用户原话同时命中多个）：见 `SKILL.md` 意图优先级 → 通常是"忠实的对话整理 → C；自己的学习体会 → D；产品发布 → B；解释概念 → A"。

### 1.2 子模式判定（仅模式 C）

| 子模式 | 触发词 | 默认适用 |
|---|---|---|
| 公众号改编 (C-publication-adapted) | "用我的 skill 转译" / 公众号 / 知乎 / Newsletter | **新默认** |
| 忠实翻译 | "忠实翻译" / "不改写" / "保留原文结构" | 学术/对照阅读 |
| 改写转述 | "内部研究" / "不要公众号调性" | 内部研究简报 |

### 1.2.1 源材料类型判定（仅模式 C，与子模式并行判定）

| 源材料类型 | 判定条件 | 骨架选择 |
|---|---|---|
| **C-dialogue**（对话转述） | 源材料含多 speaker 对话/访谈/播客 | mode-c.md "对话转述骨架" |
| **C-tutorial**（教程转述） | 源材料为 how-to / 步骤教程 / X Article | mode-c.md "教程转述骨架" |
| **C-essay**（观点转述） | 源材料为单人评论/观点文章/essay | mode-c.md "对话转述骨架"（允许简化） |

**判定方法**：
- 源材料有 ≥2 个 speaker 交替发言 → C-dialogue
- 源材料为编号步骤教程（"Step 1… Step 2…" / "10-Step Guide"）→ C-tutorial
- 源材料为单人观点论述（无步骤编号）→ C-essay
- 不确定时默认 C-essay

### 1.3 风险分级（决定跑完整路径还是快路径）

**6 项命中条件任一 → 完整路径**：

| # | 命中条件 |
|---|---|
| 1 | 原文 > 600 英文词 |
| 2 | 含代码块 / API / JSON / YAML / Prompt / CLI 命令 |
| 3 | 模式 C 对话转述（长访谈 / 播客 / 转录） |
| 4 | 技术架构 / 评测 / 论文 / 商业战略分析 |
| 5 | X / Twitter thread |
| 6 | 原文含多轮对话或人物 IP（>2 个 speaker） |

**全不命中 → 快路径**（保留最低闸门，跳过分块）。

> 注：本表 600 词阈值决定"快路径 vs 完整路径"分流；`ai-translation-guide.md` 的 1500 词阈值决定"完整路径内是否触发分块计划（阶段二B）"。两者层级不同，不矛盾。

## 二、阶段 1：翻译前（定调与策略）

### 2.1 文体调性

按 `SKILL.md` §核心调性 确认：

| 模式 | 调性锚 |
|---|---|
| A | 大白话 + 强比喻 + 痛点引入 |
| B | 专业克制 + 信息密度高 + 直接进入事实 |
| C | 记者转述感 + 大量直接引语 + 张力驱动 |
| D | 学习同伴感 + 输入-内化-输出叙事 |

### 2.1.1 媒体语感校准（所有模式强制）

按 `references/media-voice-profiles.md` 匹配目标媒体，将语感参数注入翻译 prompt：

| 步骤 | 操作 |
|------|------|
| 1 | 确认目标媒体（未指定→默认 WeChat §1） |
| 2 | 提取该媒体的 4 项核心参数：句长偏好 / 动词力度 / 开篇策略 / 技术深度 |
| 3 | 在翻译 prompt 头部注入 `🎯 目标媒体：[名称]` 锚定句（格式见 media-voice-profiles.md 末） |
| 4 | 将该媒体的禁用词/禁用表述注入翻译 prompt 的反例注入层（与确定性基座并列） |

**媒体与模式冲突时的裁决**：媒体语感参数 > 模式默认调性。例：模式 C 默认"记者转述感"，但目标媒体为 Juejin → 降低引语密度，增加代码块占比，动词向工程操作端偏移。

### 2.2 核心术语预登记

| 步骤 | 操作 | 引用 |
|---|---|---|
| 1 | 通读源材料，高亮核心 AI 术语 | — |
| 2 | 对照 `glossary-ai.md` 确定保留词/译法/加注项 | `glossary-ai.md` |
| 3 | 扫专有名词（TerminalBench / Ralph Loop / ACON 等），确定加注方式 | `cross-cultural-terms.md` |
| 4 | **ASR 转录稿专名校验**：从转录稿中提取所有疑似产品名/公司名/工具名，逐一确认"市面上有这个产品吗？" | ASR 极易把 `Claude` 误识为 `Cloud`、把连读合并为新词 |
| 5 | 标记核心判断句（定义/结论/警示/数据驱动）| 决定后续加粗 |
| 6 | 识别代码块/Prompt/引用块 | 代码块须逐字保留 |

### 2.3 翻译前语感校准（2 分钟，所有英文源材料强制）

**目的**：翻译管线的所有 post-hoc 修复可以消除翻译腔和搭配错误，但不能把"语法正确但读起来不够好"的中文变成"读起来像一流科技记者写的"。**翻译开始前，让模型先"听"好中文再动笔**——这个 2 分钟的校准步骤决定了初始翻译的质量天花板。

**执行**：

1. 根据当前模式的文体调性，从 `references/examples/translation/` 中选择 **2 个最匹配的案例文件**：
   - 模式 A（大白话专栏）→ `english-to-chinese-naturalization.md` + `metaphor-professionalization.md`
   - 模式 B（行业快讯）→ `structural-fidelity-and-quote-preservation.md` + `proper-noun-annotation.md`
   - 模式 C（对话转述）→ `long-sentence-logic.md` + 当前任务同子模式的标杆示例（如有 mode-c-publication-example.md）
   - 模式 D（认知重构）→ `english-to-chinese-naturalization.md` + `punchy-style-cases.md`
   - 技术架构/论文 → `long-sentence-logic.md` + `engineering-context-alignment.md`
   - X/Twitter 源 → `x-thread-to-mode-c.md` + `punchy-style-cases.md`

2. **Read 这 2 个案例文件**（不是 skim——关注每个案例的 ❌/✅ 对比和优化点解析）

3. 读完后在翻译 prompt 中注入一句话语感锚定：
   ```
   🎯 语感目标：译文应该读起来像 [目标中文媒体/作者风格]，不是"英文翻译过来的中文"。关键特征：[从案例中提炼的 2-3 个特征，如"短句为主、动词有力、不堆名词"]
   ```

**跳过条件**：翻译场景是**学术论文/纯技术内部文档**（语感校准对学术规范无增益）；**快路径**（阶段 1.5 判定）可压缩为只读 1 个案例。

### 2.4 文化梗与隐喻标记

| 类别 | 标记什么 | 解决路径 |
|---|---|---|
| 跨域隐喻 | `self-driving` / `run off a cliff` / `same animal` / `animal` | `translation-quickref.md` 隐喻替换表 |
| 文化梗 | `June 烤箱` / `Lyft 前身` / 美国机构缩写（PAC / 501(c)(3)） | `cross-cultural-terms.md` + 译者注 |
| 制度概念 | `pod` / `TAM` / `runway` / `pitch deck` | `cross-cultural-terms.md` + 首次加注 |
| 行业黑话 | `bull case` / `table stakes` / `moat` / `shipped` | `translation-quickref.md` 研发语境映射 |

**绝对禁止**：字面直译隐喻/制度概念，**也不**完全抛弃意译。**正确做法**：保留原词 + 补充中文锚定词（4-12 字揭示功能或争议点）。

### 2.5 L0 源 dump（所有模式 C 任务硬阻断，其他模式选做）

按 `source-inventory-protocol.md` 输出 3-4 张源材料清单：

| 清单 | 何时必做 | 通过条件 |
|---|---|---|
| 清单 1：编号 + 原文标题对 | 源材料含「N. / NN. / 一、」等编号 | 编号数 = 源材料所有编号 |
| 清单 2：分类 + 包含编号对 | 源材料含「Section / 分类 / Chapter」| 每个编号只属 1 个分类 |
| 清单 3：数字 + 单位 + 上下文对 | 源材料含数字 / 时间 / 比例 / 金额 | 每个数字都有上下文 |
| 清单 4：专有名词 / 行业术语 | 含大量术语 / 缩写 | 原文名称与源材料逐字一致 |

**任一清单写不全 → 翻译没开始 → 重新读源材料。**

### 通过条件

- [ ] 文体调性已锚定
- [ ] 核心术语表已填完（每个术语的"保留/译法/加注"已决策）
- [ ] **语感校准已完成**：已读 2 个匹配案例 + 已注入语感目标锚定句（快路径可压缩为 1 个案例）
- [ ] 文化梗与隐喻已标记
- [ ] L0 源 dump 已完成（如适用）+ 4 项硬检查全过
- [ ] 输出 `[强制输出—阶段二：轻审计闸门]` 5 项表

## 三、阶段 2：翻译中（执行与规范）

> **每翻译一段先过 5 个问题**（见 `translation-principles.md` 五条原则）：
> A. 结构脱钩了吗？B. 搭配成组了吗？C. 短句密度够了吗？

### 3.1 消灭"偷懒式"中英夹杂

**禁止保留为英文的**（除非已确认是"高共识"术语）：

| ❌ 偷懒保留 | ✅ 应译为 |
|---|---|
| `takeaway` | 核心要点 / 结论 |
| `plumbing` | 底层基建 / 管道层（语境化）|
| `asset` | 资产 / 静态资源（按语境）|
| `hype` | 炒作 / 吹捧（按语境）|
| `discipline` | 克制 / 约束 / 习惯（按语境）|
| `take` | 看法 / 立场（按语境）|
| `honest` | 诚实 / 坦率（按语境）|
| `baseline` | 基准 / 底线（按语境）|
| `framing` | 定性 / 视角（按语境）|

**可保留为英文的**（业内高度共识）：

`Prompt` / `Agent` / `Loop` / `Skill` / `PR` / `Code` / `Commit` / `Repo` / `Issue` / `CI` / `CR` / `Harness` / `Worktree` / `Sub-agent` / `Hook` / `MCP` / `Cron` / `Ralph` / `ReAct` / `Gas Town` / `Mayor Agent` 等。

**判断标准**：犹豫时默认翻译，**有意识保留**才保留。

### 3.2 抽象直译拦截（最高级翻译事故）

| 类别 | ❌ 直译 | ✅ 重译 | 原理 |
|---|---|---|---|
| **跨域隐喻** | "自驾烤箱" | 主打"自动烹饪"的智能烤箱 | 中文无"自驾烤箱"概念，必须补全产品功能 |
| **跨域隐喻** | "同一头动物" | 同一个核心 / 同一个新物种 | "动物"在中文不是抽象概念载体 |
| **物理动词+抽象宾语** | "拦下原因" / "抓住问题" / "修复想法" | 分析原因 / 厘清问题 / 完善想法 | "拦/抓/修"是物理动作 |
| **空间动词+抽象宾语** | "走进对话" / "穿过研究" | 面对对话 / 贯穿研究 | "走/穿"是空间位移 |

> 研发语境映射（动词介质/状态词/反同义反复）：见 `ai-translation-guide.md` §一.6（研发语境对齐原则）。

**机械触发**：翻译每段时，扫一遍原文所有 `discipline` / `takeaway` / `honest` / `same animal` / `under the hood` / `ball is in X's court` / `drive a bet` 等——必须查 `translation-quickref.md` 隐喻替换表。

### 3.3 网络烂梗拦截

| ❌ 烂梗 | ✅ 应替为 | 类别 |
|---|---|---|
| "按在身下摩擦" | 主导 / 占据 / 霸屏 | 饭圈 |
| "复读机" | 反复提及 / 反复引用 | 饭圈 |
| "打脸" | 否定 / 反驳 / 推翻了 | 饭圈 |
| "戳瘪" | 戳破 / 驳倒 / 否定 | 饭圈 |
| "崩了"（指系统）| 崩溃 / 宕机 / 失效 | 网络口语 |
| "烧完了"（指预算）| 耗尽 / 烧穿 / 烧光 | 网络口语 |
| "扑向"（指市场）| 抢占 / 吃下 / 切入 | 拟物不当 |
| "塞回 Agent" | 反馈给 Agent | 介质不当 |
| "把 IDE 删了" | 卸载了 IDE | 介质不当 |
| "自己下场" | 亲自参与 / 亲手执行 | 网梗 |
| "一刀切"（褒义）| 直接 / 干脆 / 明确 | 官腔 |
| "硬刚" | 对抗 / 直面 | 网梗 |

**机械触发**：每段翻译完成后 grep "崩|烧完|打脸|扑|塞回|按在.*摩擦|复读机|戳瘪" —— 任一命中即改。

### 3.4 动词介质匹配

| 介质类型 | 推荐动词 | 禁用动词 |
|---|---|---|
| 写代码 | 写 / 实现 / 构建 / 重构 | 做代码 / 制造代码 |
| 跑任务 | 跑 / 运行 / 拉起 / 启动 / 调度 | 塞任务 / 推任务 |
| 系统报错 | 崩溃 / 失效 / 宕机 / 报错 | 崩了 / 挂了 / 出错了（口语过重） |
| 部署资源 | 拉起 / 部署 / 启动 / 注入 | 放上去 / 塞进去 |
| 数据流动 | 流入 / 注入 / 灌入 / 喂入 | 塞进 / 倒进 |
| 用户操作 | 点击 / 触发 / 调用 | 戳 / 按 / 推 |

**机械触发**：每段翻译完成后扫"做.*代码|做.*功能|做.*系统|塞.*给|放上去"——任一命中即改。

### 3.5 Markdown 排版

- 所有 fenced code block 前后**必须留一个空行**（防解析器截断）
- 列表项 `-` / `1.` 前后视情况留空行
- 反引号成对；代码块起始 fence 标注语言类型
- 盘古之白：中文 + 英文/数字间加半角空格
- 引号：正式发布文体用全角弯引号 `"…"`，内嵌引号用全角单引号 `'…'`；半角直引号仅用于代码块、YAML、英文所有格、技术标识符

### 3.6 代码块与 Prompt 逐字原样保留

> 代码块/Prompt 保留规则：见 `ai-translation-guide.md` §一.4（代码块全量原样保留原则）及 §二 执行细则。

## 四、阶段 3：翻译后（审查与打磨）

### 4.1 硬错闸门（必须全过）

| 闸门 | 操作 | 引用 |
|---|---|---|
| **C2 五道机械扫描** | 原则 A 结构脱钩 / 原则 B 搭配边界 / 原则 C 密度 / 输入法残留 / 营销圈 jargon | `translation-checklist.md` + `translation-quickref.md` 机械自检 grep |

### 4.2 软错闸门（必须跑资深编辑清单）

按 `editor-polish-checklist.md` 12 节逐项过：

| 节 | 软错类型 | 优先级 |
|---|---|---|

### 4.3 数字 / 事实 / 逻辑核查

| 项 | 方法 |
|---|---|
| 数字完整性 | 原文/译文数字计数对比，差值 ≤ max(2, 5%) |
| 数字上下文保真 | 高保真锚点：原文同时出现具体数字 + 具体物体 + 时间窗口（如 `$1000/single task`）—— 三项全部原样保留 |
| 专名 / 公司背景 | 校对所有人名、公司、产品、日期（本次教训：`self-driving oven` ≠ `自驾烤箱`，`June` 是智能烤箱） |
| 因果 / 转折关系 | 英文隐含 because/which/while → 中文显式连接 `因/故/而/尽管` |
| 逻辑矛盾 | 例：原文是"对一半/错一半"，译文不可写"对一半也对一半" |

### 4.4 长句拆解

## 五、阶段 4：主编级升华（仅针对高质量长文，可选）

### 5.1 编辑注

- 在核心概念解释 / 历史脉络梳理 / 争议点反驳处插入 `> 💡 **编辑注**：[一句话提炼]`
- **数量上限**：8 章节 → 最多 8 处；建议 3-5 处为佳（过多稀释权威感）
- **目的**：防误读锚点 + 社交货币（"原来这词这么用"）
- **边界**：仅在已有事实基础上提炼，不引入源材料没有的新信息

### 5.2 译者注

- 对英文特有的幽默/双关/背景知识，添加简短译者注
- 格式：行内括号 `（即"自动烹饪"的智能烤箱）` 或文末括注 `> 📝 译者注：[英文梗的中文等效]`
- 何时用：原文用英文圈层梗（`same animal` / `infrastructure time` / `run off a cliff`）且无中文等效时

### 5.3 标题优化

按 `shared/title-workflow.md` 5 步法：

1. 分析要素：人物 / 核心观点 / 最炸裂数据 / 反常识点
2. 匹配公式（按模式适配表选 1-2 个）
3. 嵌入关键词（共享关键词库）
4. 融入个人视角（模式 A/D 必做）
5. 增加情绪钩子

**质控 7 条**（必须全过）：可读性 / 分享欲 / 20-35 字 / 避免 AI 味 / 避免营销号腔 / 信息量>形容词 / 张力检查

### 5.4 公众号改编 8 项最小交付清单

按 `SKILL.md` 公众号改编 8 项必填：

1. 顶部 clippings-style 来源标注
2. Bilingual prompt 名（仅 N 项编号列表适用）
3. Emoji section 锚（5 大类配 📝 / 🔍 / 💼 / 💻 / ⚡ / 🛠）
4. 末尾出处标注行（双标硬性格式不可省）
5. 1:1 名称对账（N×N 对账表，仅编号列表适用）
6. 跨文化术语查表（每遇 Cross-cultural 词必查 `cross-cultural-terms.md`）
7. 资深编辑 polish 清单（针对 X/Twitter + 中文读者，至少 8 处软错）
8. L0 源 dump（反"自创/漏译"硬闸）

## 八、典型软错案例（本次 mvanhorn 翻译任务的复盘）

### 案例 1：跨域隐喻直译

**原文**：`self-driving oven`

| ❌ 直译 | ✅ 重译 | 原因 |
|---|---|---|
| 自驾烤箱 | 主打"自动烹饪"的智能烤箱 | 中文无"自驾烤箱"概念；June 实际产品定位是"通过 App + 内置温度探针自动调整烹饪曲线的智能烤箱" |

**机械触发**：所有 `self-driving` / `autonomous` / `automated` 跨域用法必查 `cross-cultural-terms.md` + 译者注。

### 案例 2：抽象直译

**原文**：`infrastructure time`

| ❌ 直译 | ✅ 重译 | 原因 |
|---|---|---|
| 基础设施时间 | 系统的调度节拍 | "基础设施"+"时间"在中文无短语；"infrastructure time"=按基础设施调度跑的时间，不是字面"基础设施 + 时间" |

**机械触发**：扫所有 `infrastructure + 名词` 结构。

### 案例 3：英文隐喻直译

**原文**：`same animal`

| ❌ 直译 | ✅ 重译 | 原因 |
|---|---|---|
| 同一头动物 | 同一个核心 / 同一个新物种 | "动物"在中文不是抽象概念载体 |

### 案例 4：研发语境错位

**原文**：`discipline`（指 ralph loop 强制重置上下文的做法）

| ❌ 直译 | ✅ 重译 | 原因 |
|---|---|---|
| 纪律 | 克制 / 约束 / 固定做法 | "纪律"在中文有道德含义，技术语境必须解构 |

### 案例 5：网络烂梗

| ❌ 烂梗 | ✅ 应替为 | 类别 |
|---|---|---|
| "按在身下摩擦" | 主导 / 占据 / 霸屏 | 饭圈 |
| "塞回 Agent" | 反馈给 Agent | 介质不当 |
| "把 IDE 删了" | 卸载了 IDE | 介质不当 |
| "崩了" | 崩溃 / 失效 | 网络口语 |

### 案例 6：数字幻觉

| ❌ AI 幻觉 | ✅ 原值 | 反查 |
|---|---|---|
| 95 秒（实际是 90 秒）| 90 秒 | L0 源 dump 清单 3 数字穷尽 |
| "6 天内"（实际是"6 月 7 日发，文章 6 月 8 日发"）| 6 月 7 日 | L0 源 dump 时间戳 |

### 案例 7：逻辑矛盾

**原文**："half right"（对了一半）

| ❌ 逻辑错 | ✅ 原意 |
|---|---|
| "对了一半也对了一半" | "对了一半也错了一半" |

| ❌ 问题 | ✅ 修复 |
|---|---|
| 代码块（```bash）前后未留空行 | 前后各留一个空行 |

## 十、何时跳过本 SOP

- **中文源材料**：阶段 1.5 / 阶段 2 L0 源 dump 数字部分保留，术语部分按 glossary；其他阶段 2-3 软错闸门仍跑
- **超短英文材料**（< 200 词）：走快路径，阶段 2-3 软错层可压缩为单遍
- **学术论文翻译**：`discipline` / `takeaway` 等学术黑话可保留英文（学术规范）
- **代码内部文档**：可不跑 §5 主编级升华
